## 2. Findings

### 2.1 Opcode inventory (VERIFIED, OPS)

- Hashing: `OpBlake2bWithKey` 0xa7 (775, key up to 64 bytes via `blake2b_simd::KEYBYTES`), `OpSHA256` 0xa8 (785), `OpBlake2b` 0xaa (797), `OpBlake3` 0xd9 (1456), `OpBlake3WithKey` 0xda (1465, 32-byte key). Pricing: `HashOpcodePricing` OPS:55-73 (Blake2b 2, Blake3 1, SHA256 1 script unit per byte).
- Signatures over the transaction sighash: `OpCheckSig` 0xac (827, Schnorr, secp256k1 x-only key), `OpCheckSigECDSA` 0xab (804), `OpCheckMultiSig`/`...ECDSA` (860, 793), `...Verify` variants. The signed message is the transaction sighash (`check_schnorr_signature` calls `calc_schnorr_signature_hash`, `RK/crypto/txscript/src/lib.rs:847-854`). Not usable for arbitrary data.
- Signatures over a script-chosen message: `OpCheckSigFromStack` 0xd7 (1438) and `OpCheckSigFromStackECDSA` 0xd8 (1447). Stack inputs are signature, 32-byte message hash, pubkey. The message hash is taken directly from the stack (`check_schnorr_signature_with_msg_hash(..., |_| msg_hash)`). So an oracle-signed value is verifiable on-chain. Nothing in the engine binds the message to the transaction.
- ZK: `OpZkPrecompile` 0xa6 (759). Tags Groth16 (BN254) and RISC Zero succinct (Poseidon2 only; SilverScript marks blake2b and sha256 variants "reserved", `builtin.rs:~321`).
- Chain data: `OpChainblockSeqCommit` 0xd4 (1389). Other introspection: `OpTxInputDaaScore` 0xc0 (1124, the DAA score of the spent UTXO, not the current block), `OpTxLockTime` 0xb5 (995). I found no opcode for the current block's DAA score, hash or blue work. The "grep" for `Block|Blue|Prun|Daa` opcodes found only the ones listed. UNVERIFIED in the sense that I did not read every opcode body in the 0x00-0xff range, but the opcode list scan above covers the named categories.
- Arithmetic is `i64` only (`OpMul` etc., OPS:649-668; `OpLShift` disabled, OPS:670). No BLS12-381 or pairing code: `rg` over `crypto/txscript` for `bls12|bls381|pairing` returned no source files; the only curve crates are `ark-bn254` (`crypto/txscript/Cargo.toml:20-25`).
- Limits (KIP-17 `refs/kips/kip-0017.md:~95-113`): post-Toccata MAX_SCRIPT_ELEMENT_SIZE 1,000,000, MAX_SCRIPTS_SIZE 1,000,000, MAX_OPS_PER_SCRIPT 1,000,000; transient mass binds first. Engine constants: `MAX_STACK_SIZE = 244` (`lib.rs:77`). Block mass limits: compute 500,000, storage 500,000, transient 1,000,000 (`params.rs:626`). Resource meter: `RK/crypto/txscript/src/runtime_resource_meter.rs` (sigops and pushed bytes charged in script units against a committed budget).

### 2.2 KIP-21 `OpChainblockSeqCommit`

- Returns the header's `accepted_id_merkle_root` of block X, which post-activation is `SeqCommit(X)` (`refs/kips/kip-0021/seqcommit-accessor.md`, "Opcode Mechanics"; OPS:1389-1404; `consensus/src/model/services/seq_commit_accessor.rs:36-44`). VERIFIED.
- What is committed (`refs/kips/kip-0021.md` section 6): `SeqCommit(B) = H_seq(SeqCommit(selected_parent(B)), SeqStateRoot(B))`. `SeqStateRoot` combines ActivityRoot (inactivity shortcut plus the active-lanes sparse Merkle root over lane tips, where lane id = tx `subnetwork_id`), MergesetContextHash (selected-parent timestamp, B's DAA score, B's blue score), and MinerPayloadRoot (Merkle root over, for each mergeset block, its hash, blue work and coinbase payload hash). VERIFIED. So it is not a plain block hash and not a plain transaction root.
- Depth window: the accessor admits X only when `X.blue_score + F > P.blue_score`, with P the selected parent of the validating block (`seq_commit_accessor.rs:10-12, 36-44`; `seqcommit-accessor.md` "Access Threshold"). F is the node's `finality_depth` (`utxo_validation.rs:373, 445`) = `BPS * FINALITY_DURATION`, `FINALITY_DURATION = 43_200` s (`consensus/core/src/config/constants.rs:70`; `config/bps.rs:92-94`). The accessor doc says "about 12 hours of target block time". The unit is blue score, so the wall-clock figure depends on the actual block rate. The 12 h prior note is VERIFIED as the nominal value; the BPS value for mainnet (10, `TenBps` imported in `params.rs:2`) is UNVERIFIED as to which params struct is selected for each network.
- Failure modes: `BlockAlreadyPruned` (unknown), `BlockNotSelected`, `BlockIsTooDeep` (OPS:1394-1401). VERIFIED.
- Reorg: the opcode is re-evaluated from the new point of view; a transaction fails if X is no longer on the selected chain, and the UTXO state rolls back (`seqcommit-accessor.md` "Reorg Behavior"). VERIFIED. Consequence for any consumer: a draw that used X can be invalidated by a reorg and must be re-mined against a block still on the chain (inference).
- Predictability and grinding: the KIP and refs contain no statement about randomness, beacons or miner manipulation (`rg -il "randomness|beacon"` over `refs/kips`, `RK/docs`, `SS/docs` found only a bundled mermaid.js). Inputs to `SeqCommit(X)` that other parties can affect, read from the spec (inference, UNVERIFIED as a security analysis): the miner of X chooses which blocks and transactions form its mergeset, its coinbase payload is part of the data committed by the chain block that merges it, and any user can add transactions to the native lane or any user lane, changing lane tips. A miner can also withhold X. The size of the grinding space and its cost were not quantified by any source I found.
- Web: I found no Kaspa research-forum or KIP discussion of using `OpChainblockSeqCommit` as a randomness beacon. A web search (extended) returned only an unreviewed Substack post combining Bitcoin and Kaspa block hashes (https://kodinglsfun.substack.com/p/a-verifiable-cheatresistant-hybrid; a single-author claim, UNVERIFIED) and general beacon-grinding literature (https://eprint.iacr.org/2025/1974.pdf, https://arxiv.org/pdf/2205.13333). The forum URLs cited in the accessor doc (https://research.kas.pa/t/208, /258) concern based zk-rollups, not randomness; I did not fetch them.

### 2.3 External beacons

- drand: BLS12-381. Schemes `pedersen-bls-chained`, `pedersen-bls-unchained` (public key in G1, signature in G2) and `bls-unchained-on-g1` (signature in G1, key in G2); unchained message is H(round), chained is H(round || previous signature); the round value is H(signature) (https://docs.drand.love/docs/cryptography, fetched 2026-10-12). No secp256k1 or Schnorr option was listed. Kaspa v2.1.0 has no BLS12-381 or pairing operation (2.1), so a drand signature cannot be checked natively. Only indirect: a Groth16 (BN254) or RISC Zero proof that a BLS signature verified, with the cost in row E. Not tested here; UNVERIFIED that such a circuit is practical within 140,000 grams.
- Schnorr oracle: natively verifiable with `OpCheckSigFromStack` (row B). The script chooses and checks the message, so the covenant can require a message containing round id and fixed fields. Properties are those of any trusted signer (equivocation if the message is not pinned; withholding; key compromise). The oracle's own randomness source is outside script verification.
- VDF: no native big-integer arithmetic (2.1), so a Wesolowski or Pietrzak verifier cannot be written in script. Via ZK it is a proof of the verification statement (row E). No cost measurement exists in the refs. UNVERIFIED.
- Compute-limit framing: the 500,000 is the per-block compute mass limit (`params.rs:626`), so it is also the ceiling for one transaction. Groth16 alone uses 28% of it (140,000 / 500,000) and R0 succinct 50%.

### 2.4 Commit-reveal on UTXO chains

- Failure modes (Cardano developer guide, https://developers.cardano.org/docs/developers/curriculum/dapps/oracles/randomness/, fetched 2026-10-12): the last revealer has seen every other value and can withhold; a determined one can force a restart even if they cannot choose the outcome; mitigation is a deposit forfeited on non-reveal, a deadline bound (validity interval) so the protocol can resolve or refund; combine by sorting and hashing, not XOR (late committer can cancel). The same page lists block and transaction hashes as grindable and block producers as able to withhold and retry.
- Commit-Reveal2 (https://arxiv.org/abs/2504.03936): randomised reveal order plus on-chain recovery path and slashing (per search summary only; not read in full, UNVERIFIED).
- "Non-rerollable fallback" in published designs: the Cardano guide offers only refund/resolve and deposit forfeiture. I found no published UTXO design with a fallback that cannot be re-rolled; that remains open.
- On Kaspa, covenant checks are one-sided in time (project rule R3; deadlines are absolute DAA scores, lower-bound checks only), so a reveal deadline cannot be enforced as an upper bound on when a reveal is accepted. Forfeiting after a deadline is implementable as a lower-bound-gated claim. This is inference from the project rules, not from a ref.

## 4. External input: Michael Sutton (Kaspa core) on Toccata randomness, 2026-10

Source: a direct exchange between the project owner and Michael Sutton, pasted into the project session on 2026-10-13. Quoted as a primary source from a consensus author; it is an opinion and a design framing, not a measured result, so its claims are labelled as his, not VERIFIED against the refs unless noted.

Question asked: with Toccata, does Kaspa gain a path to trustless, unbiasable on-chain entropy without an external oracle, and do the ZK opcodes or covenants change what is possible?

His short answer, verbatim:

> pow-backed block hashes are considered a good source of randomness but you need to make sure the mechanism cannot selectively choose what hashes to use.
> accessing such hashes directly from the script engine is a bit tricky (but not impossible).
> based apps have an easier path through the kip21 sequencing commitment, but here to the design must be cautious and not give too much selection power to the mechanism/ the zk prover

His extended answer, in summary (points that matter to this project):

- A block hash is the output of the PoW lottery: unpredictable before the block is found, known to its miner first. The miner can withhold or publish strategically, so the party who sees the hash first can decide whether the application ever consumes it. The mechanism must remove that choice by binding to a hash already fixed in the selected-parent chain, with no retry among several recent candidates.
- Toccata adds no randomness opcode. KIP-17 introspection exposes transaction fields, not historical block hashes. The closest chain-data opcode is `OpChainblockSeqCommit` (0xd4): it takes a block hash and, if the block is on the selected-parent chain, known, post-activation and within the access window, returns its sequencing commitment (post-KIP-21 `accepted_id_merkle_root`). The window is the finality depth, roughly the last 12 hours of blue score; outside it the script fails; a reorg re-evaluates the check and a transaction referencing a block that left the chain becomes invalid. (Consistent with row A and §2.2 above: VERIFIED in the refs.)
- KIP-21 commits to ordered activity (lanes by subnetwork, lane tips in a sparse Merkle tree, one 32-byte commitment per header), which is the easier path for based apps with a ZK prover. The remaining bias surface is selection inside the allowed window: if the prover or the covenant can pick which recent block's commitment to use after seeing several, or delay settlement until a favourable anchor appears, the entropy is no longer unbiasable.
- Design requirement, his words: fix the anchor in advance, "for example, the seqcommit of the chain block at a predetermined blue-score offset", so neither the miner nor the prover retains a menu of hashes. A covenant must hard-bind the entropy source to a non-selectable, already-committed chain value inside the finality window.

Consequences recorded in `docs/DECISIONS.md` (2026-10-13):

1. The project's two-transaction shape (`close()` stores an absolute seed reference before the source exists; `draw()` is lower-bound locked at it and reads one fixed anchor) is the shape he describes. This project reads the commitment directly in the covenant with no prover, so the only selection surface is the miner of the anchor block.
2. Open: he addresses the anchor by **blue score**; the project stores `seed_ref` as a DAA score (rule R3). The KIP-21 window check is also in blue score. Chain blocks do not occupy every blue-score value, so the rule must be of the form "the first chain block with blue score ≥ B", and `draw()` must be able to verify that the presented block is that one (e.g. via the commitment's preimage fields and the selected parent's commitment). To be specified in the randomness milestone.
3. Open: the cost of the anchor miner withholding its block (one "re-roll" at the price of that block) is unquantified; see §3 item 1.
4. Open: the 12 h window makes a missed-draw fallback mandatory (design §10, §11).

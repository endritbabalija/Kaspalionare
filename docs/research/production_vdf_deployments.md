# VDFs in production and serious protocol engineering (status as of October 2026)

Scope note: this file covers every real deployment or major engineering effort I could verify that uses a VDF / slow function / time-lock to make blockchain randomness unbiasable. Status dates are given per fact. "Abandoned/superseded" items are marked explicitly. Primary sources (project docs, GitHub, ePrint, official blogs) are preferred; where only secondary sources exist, this is flagged.

Headline summary (for the report writer):
- Only two L1s run a VDF for randomness on mainnet today: **Chia** (class-group Wesolowski VDF, live since March 2021, ASIC timelords since late 2023) and **Tezos** (class-group Wesolowski VDF post-RANDAO, live since the Kathmandu upgrade, Sept 2022). **Autonomys/Subspace** runs an AES-based "proof-of-time" (explicitly "not technically a VDF") since Nov 2024. **Harmony** has VDF code in its node (difficulty 50,000, ~100 s) but I could not confirm it is active on mainnet (see gaps).
- **Ethereum's** VDF program (RSA-2048 → Ligero MPC → MinRoot) was **paused in September 2023** after the EF-commissioned MinRoot cryptanalysis showed ~20x parallel speedups with 2^29 processors; EF statement: "At present we do not recommend using VDFs within Ethereum." Ethereum uses RANDAO (1 bit of bias per tail proposer) and in July 2026 published a draft EIP-8321 (hash-chain RANDAO) that keeps the same bias model.
- **StarkWare VeeDo** (STARK-proven algebraic VDF) went live on Ethereum mainnet as a PoC in June 2020; its sequentiality assumption was later broken in the same CRYPTO 2024 paper that broke MinRoot. No evidence it is still operated.
- **Unicorn/sloth** (2015) is the conceptual ancestor; the only documented running instance was the authors' "trx" curve-generation service; academic beacons (Breeding Unicorns, Random UChile) prototyped it.
- Expert consensus 2024–2026: algebraic/field-based VDFs (Sloth++, VeeDo, MinRoot) are not trusted; repeated squaring in RSA or class groups remains the only deployable construction, with class groups needing ~1208-bit+ discriminants per Dobson–Galbraith–Smith (Chia and Tezos use 1024-bit); VDFs cannot exist in the random oracle model (Guan–Riazanov–Yuan, CRYPTO 2025), so structured algebraic assumptions are unavoidable; economic-security analysis (Shang–Chen, Apr 2026) argues few-second VDF delays are economically insecure.

## Key Question 1: Chia Network — proof of time / timelords

### Takeaway
Chia is the longest-running production VDF deployment: repeated squaring in a class group of a 1024-bit prime discriminant (fresh discriminant per infusion), proved with Wesolowski proofs (first a fast 64-element "n-Wesolowski" proof, later replaced by a 1-element proof). ASIC timelords built with Supranational went live on mainnet in October/November 2023 at a forecast 800k–1M iterations/s (~3–4x the fastest CPU timelord at ~260k IPS); Chia's security argument is that the attacker's space requirement is a function of relative VDF speed (42.7% with equal-speed unlimited timelords, 33.3% with a single 2x-faster timelord), and that challenges are "almost ungrindable" (challenge depends only on the first block infused per sub-slot, ~32 combinations of grinding).

### Cited Findings

**Construction and parameters**
- The VDF is repeated squaring in a class group of unknown order; Chia chose class groups over RSA to avoid a trusted setup ("An RSA group would require an MPC ceremony"). Initial element a=2, b=1; "Each VDF gets its own discriminant, a random prime derived from the challenge." "The discriminant has a size of 1024 bits, which means the proof sizes are around 1024 bits." — [Chia docs: Proof of Time](https://docs.chia.net/proof-of-time)
- Proofs use the "Wesolowski scheme, split into n (1<=n<=64) phases so that creating the proofs is very fast"; n-Wesolowski proofs are later swapped for 1-Wesolowski proofs (smaller, slower to produce); proofs are not committed on-chain so they can be replaced. The docs admit "classgroup code is less tested in real life" than RSA. — [Chia docs: Proof of Time](https://docs.chia.net/proof-of-time)
- Chia Green Paper (Oct 2024): sequential function is "repeated squaring in class groups of unknown order"; "A fresh group is sampled every time a value is infused"; Wesolowski "proof of size only one group element"; the deployed implementation "first computes a larger, faster proof of 64 group elements, which is later replaced by the one-element proof." — [Chia Green Paper 2024-10-08](https://docs.chia.net/files/ChiaGreenPaper_20241008.pdf)
- Mainnet consensus constants in `default_constants.py`: `DISCRIMINANT_SIZE_BITS = 1024`, `SUB_SLOT_ITERS_STARTING = 2**27` (134,217,728), `SUB_SLOT_TIME_TARGET = 600` s, `NUM_SPS_SUB_SLOT = 64`, `NUM_SP_INTERVALS_EXTRA = 3`, `MAX_SUB_SLOT_BLOCKS = 128`, `EPOCH_BLOCKS = 4608`, `SUB_EPOCH_BLOCKS = 384`, `DIFFICULTY_STARTING = 7`, `HARD_FORK_HEIGHT = 5496000`. — [chia-blockchain default_constants.py](https://github.com/Chia-Network/chia-blockchain/blob/main/chia/consensus/default_constants.py)
- `constants.py` comment on DISCRIMINANT_SIZE_BITS: "Max is 1024 (based on ClassGroupElement int size)". — [chia-blockchain constants.py mirror](https://git.sudo.is/mirrors/chia-blockchain/src/branch/main/chia/consensus/constants.py)
- A sub-slot is "always targeted to last 10 minutes" with a target of 32 winning proofs per sub-slot; three VDFs run concurrently (challenge chain, reward chain, infused challenge chain); sub-slot iterations and difficulty adjust at epoch/sub-epoch boundaries. — [Chia docs: Challenges](https://docs.chia.net/consensus-challenges/)
- Three VDF chains: 64 signage points per sub-slot released about every 9.375 s on average; target 32 blocks per sub-slot, minimum 16 reward-chain blocks per slot, maximum 128. The infused challenge chain "increases security by preventing VDF lookahead attacks." — [Chia docs: Three VDF Chains](https://docs.chia.net/three-vdf-chains/)
- chiavdf library: main loop computes repeated squarings using NUDUPL with custom GCD and master/slave threading; "Simple Wesolowski proofs" and nested n-Wesolowski proofs chaining up to 64 intermediate proofs; proofs can cover up to 2^36 iterations; AVX-512 IFMA runtime flags; Apache-2.0; benchmark command `./vdf_bench square_asm 250000`. — [chiavdf GitHub](https://github.com/Chia-Network/chiavdf)

**Verification cost**
- Chia docs say a verifier can check a proof "without redoing the computation" but give no concrete verification cost. — [Chia docs: Proof of Time](https://docs.chia.net/proof-of-time)
- Generic Wesolowski verification "requires essentially two exponentiations in the group G, with exponents of bit-length the security parameter k"; in the 2048-bit RSA example, "around 270 multiplications in G" and proofs of 0.25KB. — [Wesolowski, Efficient VDFs (ePrint 2018/623)](https://eprint.iacr.org/2018/623.pdf)
- Bluebox timelords recompute historical uncompressed (n-Wesolowski) proofs into compact proofs that are "faster to validate," helping low-powered nodes sync. — [Chia docs: Timelord Architecture](https://docs.chia.net/timelord-architecture/)

**Timelord hardware landscape and speeds**

- Chia–Supranational partnership announced Oct 13, 2021 for VDF hardware acceleration ("timelords"), targeting launch in H2 2022; Bram Cohen: "The world's best proof of time is about to become the world's fastest, and by extension, safest." No numbers in the release. — [BusinessWire, Chia Partners With Supranational](https://www.businesswire.com/news/home/20211013005324/en/Chia-Partners-With-Supranational-to-Create-Industry-Leading-Proof-of-Space-Time-Security)
- "We're going to ludicrous speed" (Oct 26, 2023): ASIC timelords forecast at "somewhere between 800,000 iterations per second (IPS) and 1,000,000 IPS" vs. fastest non-ASIC timelords "in the 260,000 IPS range"; "fully operational by November 9th, 2023"; price "$1000 dollars per Timelord," clusters of three at $3,000; applications Dec 1, 2023–Jan 1, 2024, shipping late Jan 2024. Rationale: ASICs "increase the difficulty for attackers to control the generation of challenges and infused blocks." — [Chia blog, Ludicrous Speed](https://www.chia.net/2023/10/26/were-going-to-ludicrous-speed/)
- Timelord architecture docs: first ASIC batch received 2023, "about four times faster than the fastest non-ASIC timelords"; activated on mainnet October 2023; a three-VDF ASIC cluster "could hit upwards of one million IPS"; "We expect the current crop to remain the fastest timelords in the world for years to come"; future redesigns "costly and near physical limits"; only the fastest timelord broadcasts; a faster attacker timelord could run a long-range attack with less than 42.7% of netspace; Chia aims to "push timelord speeds toward silicon limits and keep VDF hardware designs open." — [Chia docs: Timelord Architecture](https://docs.chia.net/timelord-architecture/)
- June 10, 2024 rollout post: community purchasers "around the world" received units, "a dozen new countries" joined; no counts or IPS published; distribution map withheld "to protect the anonymity of the purchasers." — [Chia blog, Global Expansion of ASIC Timelord Rollout](https://www.chia.net/2024/06/10/global-expansion-of-chia-network-security-with-successful-asic-timelord-rollout/)
- Troubleshooting docs show mainnet network-estimated IPS on 2024-04-11 of ~552k–575k per chain (REWARD_CHAIN 575,336.2; INFUSED_CHALLENGE_CHAIN 558,173.6; CHALLENGE_CHAIN 552,043.3), noting network-estimated IPS "will be lower than the IPS reported by the ASIC software"; ASIC frequency is tuned via `--auto-freq 60`; default voltage 0.88 V. — [Chia docs: Timelord troubleshooting](https://docs.chia.net/troubleshooting/timelords); [Chia docs: Timelord install](https://docs.chia.net/timelord-install/)
- Timelord install docs: "Software timelords … should be used only for experimentation," "the ASIC cluster will always have an advantage" because VDFs cannot be split across machines; recommended host "modern gaming PC with minimum 6 fast cores and 8GB of RAM"; "at least three fast CPU cores are necessary" since three VDF chains run in parallel. — [Chia docs: Timelord install](https://docs.chia.net/timelord-install/); [Chia docs: Timelord algorithm](https://docs.chia.net/timelord-algorithm)
- Academic ASIC designs for Chia-style class-group squaring: Zhu et al. (Nanjing U., ~2022) 2048-bit-discriminant design in TSMC 28nm at 455 MHz, 7.1 µs per squaring+reduction, 3.6x faster than Chia's C++ on an i9-9900X (25.6 µs); they argue "the fastest implementation should be publicly known." — [ePrint 2022/755](https://eprint.iacr.org/2022/755.pdf). Sreedhar–Horowitz–Torng (Stanford, 2021–22) XGCD accelerator for 1024-bit class-group squaring on SKY130 (180–130nm), 3 ns cycle, ~3.7 µs/computation, "10X" vs prior class-group accelerator and 4X vs Chia software. — [ePrint 2021/1292](https://eprint.iacr.org/2021/1292/20210927:130322)

**Competitions (2018–2019)**
- Round 1 (closed Jan 3, 2019): bulaiden 40.65 s vs reference 169 s (track 1); $40k first, $20k second, $2k per other team; total $116k; discriminant-breaking Track 2 postponed. — [Chia blog, VDF Competition Round 1](https://www.chia.net/2019/01/17/chia-vdf-competition-round-1-results-and-announcements/)

**Security analysis / unbiasability**
- Consensus attacks page: majority-attack space thresholds by timelord speed: 66.7%, 59.8%, 50.0% (single 1x timelord), 42.7% (unlimited timelords at 1x; worst case for extending-chains attack), 33.3% (single 2x timelord), 25.4%; 27.1% for infinite 2x timelords over >1 epoch; double-dip advantage peaks "with a timelord that is somewhat less than twice as fast as the fastest honest timelord"; faster timelord "can allow an attacker to orphan certain blocks" and makes long-range attacks more effective; below 40.5% of space "the usefulness of the faster timelord decreases substantially"; grinding limited to ~32 combinations (5 PiB can appear as 6–7 PiB). Chia "has developed and distributed ASIC timelord" globally to reduce attacker access to fast timelords. — [Chia docs: Consensus attacks](https://docs.chia.net/consensus-attacks/)
- Green Paper: provable security requires `space_h · vdf_h > space_a · vdf_a · 1.47`; double spending possible if `space_h · vdf_h < space_a · vdf_a · 1.34` (≈43% of space at equal VDF speed); double-dipping boost of 1.47 with k=16 blocks (vs factor e≈2.718 for the naive design); the trunk is "(ALMOST) ungrindeable," with timestamps "a minor grinding opportunity"; adversary "may control an unbounded number of VDFs of speed vdf_a"; "only requires a single timelord (which runs 3 VDFs) to be active at any time." — [Chia Green Paper 2024-10-08](https://docs.chia.net/files/ChiaGreenPaper_20241008.pdf)
- Three VDF Chains page: the challenge-chain lottery is "completely pre-determined, and not affected by blocks in the slot, until the end of the slot"; only the first block infused in a slot affects the next challenge; withholding/adding later blocks cannot change it — this is the anti-grinding design. — [Chia docs: Three VDF Chains](https://docs.chia.net/three-vdf-chains/)
- a16z crypto (Bonneau & Nikolaenko, Oct 2022): Chia "implements a version of this as part of its consensus protocol, using repeated-squaring VDFs in class groups" — the only chain they describe as running VDFs in consensus. — [a16z crypto, Public Randomness and Randomness Beacons](https://a16zcrypto.com/posts/article/public-randomness-and-randomness-beacons/)

**Incidents / design changes since 2021**
- Sept 10, 2021 (v1.2.6): a bug "around since the launch of mainnet" surfaced when Chia deployed "100+ Bluebox Timelords" and nodes could not keep up with the queue of incoming compact proofs, exhausting memory ("node and system instability"); Blueboxes taken offline; fix in 1.2.6. Availability issue, not a consensus/security break. — [Chia blog, Important version 1.2.6 information](https://www.chia.net/2021/09/10/important-version-1-2-6-information/)
- Oct 2023: ASIC timelords activated on mainnet (design change: hardware timelords replace CPU ones as the fastest). — [Chia docs: Timelord Architecture](https://docs.chia.net/timelord-architecture/)
- Mainnet `HARD_FORK_HEIGHT = 5496000` in constants (the 2.0 hard fork; not VDF-specific). — [chia-blockchain default_constants.py](https://github.com/Chia-Network/chia-blockchain/blob/main/chia/consensus/default_constants.py)

### Inferences
- ASIC-to-CPU speedup on mainnet is ~3–4x (800k–1M vs 260k IPS); network-measured ~555k–575k IPS in April 2024 suggests production ASICs run at roughly 2x the best 2023 CPU numbers once proof-generation overhead and the "network-estimated" discount are included.
- Chia's unbiasability claim rests on (a) grinding bounded to ~32 choices per sub-slot by the first-infused-block rule and (b) the assumption that no attacker has a timelord materially faster than the public ASICs. The second assumption is enforced socially/economically (open designs, $1000 units distributed globally), not cryptographically.
- Chia's 1024-bit discriminant is below the ~1208-bit level that Dobson–Galbraith–Smith argue is needed against L(1/2) class-group order algorithms (see Q6); Chia mitigates by rotating the discriminant every infusion (~every 10 minutes per Neodyme), so an order computation must finish within one sub-slot to matter.

### Gaps
- No primary source publishes the exact ASIC process node, die details, or the Supranational design files; the "ludicrous speed" post names only "research and fabrication partners."
- No official Chia figure for per-proof verification time (ms) or for how many ASIC units were produced/distributed.
- I found no Chia security incident involving a timelord being out-sped or VDF proof forgery; absence of evidence, not evidence of absence.

## Key Question 2: Ethereum's VDF program and what Ethereum uses today

### Takeaway
Ethereum's VDF effort ran 2018–2023: an RSA-2048 Wesolowski beacon (Justin Drake's "minimal VDF randomness beacon," A_max=10 example) backed by the VDF Alliance (EF + Protocol Labs/Filecoin + Supranational, 2019) whose FPGA contest cut 1024-bit modular squaring from 50 ns to 25.2 ns/sq; the RSA MPC ceremony (Ligero/Diogenes) was broken by ZenGo's "DogByte" audit (Aug 2020), prompting a pivot to the field-based MinRoot (Nov 2022), which the EF-commissioned Lyon workshop (Apr 2023, report Sept 2023) showed could be parallel-accelerated ~20x with 2^29 processors; the EF then stated "At present we do not recommend using VDFs within Ethereum" (Sept 18, 2023). Ethereum still uses RANDAO, biasable by one bit per tail-slot proposer; multiple 2023–2025 studies find no statistically significant mainnet manipulation but show a 28–33% staker can control a chosen future slot with ~65–99.5% probability.

### Cited Findings

**Original design (2018)**
- "Minimal VDF randomness beacon" (Justin Drake, Sept 26, 2018): 8-second slots, 128-slot epochs; RANDAO produces per-epoch entropy e_i; r_i = D(e_i, T) is the VDF output; T set so commodity hardware takes A_max epochs; worked example A_max = 10 justified by a "$20m-$30m" ASIC budget; Wesolowski VDF with "a 2048-bit RSA modulus, or a 2048-bit class group discriminant"; proof overhead 512 bytes/epoch, verification ~1 ms; hardware "at least 18 months"; EF and Filecoin (possibly Chia, Solana) to co-develop the ASIC; fallback to RANDAO if the VDF breaks; Drake preferred an RSA MPC over class groups. — [ethresear.ch: Minimal VDF randomness beacon](https://ethresear.ch/t/minimal-vdf-randomness-beacon/3566)
- Drake, Oct 12, 2018: plan "to use the Wesolowski VDF with an RSA modulus generated through an MPC, similar to Zcash's Powers of Tau"; class groups "an option but involve tradeoffs." — [ethresear.ch: VDFs and RANDAO manipulability](https://ethresear.ch/t/verifiable-delay-functions-and-randao-manipulability/3777)
- Drake, Sept 21, 2018: EF in discussions with Obelisk Launchpad for a turn-key ASIC; estimates "3 mm^2" die area, ~10 W per evaluation, "~$20m state-of-the-art commodity VDF ASIC"; "There is no rush to deliver the hardware"; phase 0 proceeds without VDF. — [ethresear.ch: Collective Coin Flipping CSPRNG #26](https://ethresear.ch/t/collective-coin-flipping-csprng/3252/26)
- Feb 7, 2019 (CoinDesk via DiarioBitcoin): EF evaluating a "USD $15 million" VDF investment; Filecoin provisionally agreed to share the feasibility-study cost; planned RSA ceremony with "hundreds of randomly selected people" and a global circuit competition; go/no-go in ~4 months. Secondary source (Spanish translation of CoinDesk). — [DiarioBitcoin](https://www.diariobitcoin.com/noticias/fundacion-ethereum-evalua-inversion-de-usd-15-millones-para-desarrollo-de-tecnologia-vdf)
- Oct 29, 2018 StarkWare/EF STARK session notes: Ethereum planned an RSA-based scheme ("not quantum secure," requires trusted setup), T targeted "around one hour," proof released within ~1.01T, dedicated ASIC funded by EF and distributed free; StarkWare's position: STARKs "do not currently appear to be an optimal VDF solution." — [notes.ethereum.org STARK session](https://notes.ethereum.org/b8DsLbLcRmKHlWAXEXt_Rw)

**VDF Alliance and FPGA competition (2019–2020)**
- Protocol Labs + EF collaboration announced April 19, 2019: "design and develop at least one secure, efficient, and usable VDF construction"; preliminary research into whether optimized ASICs are viable; co-funded grants (no amounts); later efforts may include public optimization contests, public MPC for security parameters, hardware development. — [Protocol Labs blog, Collaboration on VDFs](https://pl.xyz/blog/collaboration-on-vdfs)
- VDF Alliance home: began early 2019 to assess feasibility of fast open VDF hardware; built CPU and FPGA RSA VDF implementations used to solve MIT's 20-year LCS35 puzzle in two months; open-sourcing designs. — [VDF Alliance wiki overview](https://supranational.atlassian.net/wiki/spaces/VA/overview)
- Evaluator ASIC design page (last updated Jul 31, 2019): fixed-function chip with a 2048-bit Modular Squaring Unit (MSU) against a predefined 2048-bit RSA modulus; targets (all marked estimates/TODO): ~10 W power, "2 ns" modular squaring latency, difficulty "on the order of 2^40," I2C control, 0.75 V logic. No tapeout, process node, cost or date given. — [VDF Alliance: Evaluator ASIC Design](https://supranational.atlassian.net/wiki/spaces/VA/pages/36569089/Evaluator+ASIC+Design)
- FPGA competition (vdf-fpga repo): goal "fastest (lowest latency) 1024 bit modular squaring circuit possible targeting the AWS F1 FPGA platform" (Xilinx VU9P); `MOD_LEN = 1024`; Round 1 t=2^30; Round 2 t=2^33 (~4 minutes), prize "$5000 / ns improvement over the baseline," baseline 28.6 ns/sq; up to $100k across two rounds. Note the modulus was **1024-bit**, not the 2048-bit production target. — [supranational/vdf-fpga GitHub](https://github.com/supranational/vdf-fpga)
- Round 1 report (Oct 14, 2019): latency reduced "from 50 ns/sq to 28.6 ns/sq" (Ozturk baseline → Eric Pearson's eric_pearson-2 entry); 30 individuals / 18 teams signed up, 10 submissions from 5 teams, 2 fully working; AWS F1 at $1.65/hr. No CPU baseline given in the report. — [VDF FPGA Competition Round 1 Report (PDF)](https://supranational.atlassian.net/wiki/download/attachments/49545221/VDF+FPGA+Competition+Round+1+Report.pdf?version=1)
- Round 2 page (Oct 16–Dec 31, 2019): baseline 28.6 ns/sq, 309-digit (~1024-bit) modulus; Justin Drake (Nov 26, 2019): "the prize for shave 20ns (getting it from 28.6 ns/sq to 8.6 ns/sq) is $100K." — [VDF Alliance: FPGA Competition Round 2](https://supranational.atlassian.net/wiki/spaces/VA/pages/48758785/FPGA+Competition+Round+2)
- Round 2 results: Eric Pearson wins at **25.2 ns/sq** (eric_pearson-2); Geriatric Guys with Gates 26.4 ns/sq; eric_pearson-1 27 ns/sq; xjtu_asic 30.8 ns/sq (DRC fail); "The final round for lowest latency design using an alternative representation closes at the end of January" (2020). — [supranational/vdf-fpga-round2-results](https://github.com/supranational/vdf-fpga-round2-results)
- Jane Street (June 22, 2020) says its "Predictive Montgomery" design won "the third and final round": 46 ns/op at 65 MHz but 2.3x less area (201 vs 464 KLUTs) and 3.7x less power (4.9 vs 18.3 W) than Ozturk's 25.2 ns/op design; techniques not efficiently possible on GPUs or CPUs; no CPU benchmark. — [Jane Street blog, Really low latency multipliers](https://blog.janestreet.com/really-low-latency-multipliers-and-cryptographic-puzzles/)

**RSA MPC ceremony broken (2020)**
- ZenGo "DogByte" (Aug 31, 2020): reviewed Ligero's Diogenes RSA-modulus MPC (LigeroRSA) at the request of the VDF Alliance and EF with Profs. Orlandi and Scholl; two individually-safe optimizations (packed ciphertexts + revealing randomness for "bad" candidates without ZK proofs) combined let "any passive observer … covertly learn the secrets p,q" via Gaussian elimination; disclosed responsibly, authors working on a fix (ZK proofs for all candidates, adding minutes to a <20-minute protocol). — [ZenGo, DogByte Attack](https://zengo.com/dogbyte-attack-playing-red-team-for-eth2-0-vdf/)
- EF statement (Sept 2023): "The team's first VDF attempt was RSA-based, which needed a trusted setup. An audit by ZenGo found an attack on the planned multiparty computation for that setup, so the team moved to MinRoot." — [ethresear.ch: Statement regarding the MinRoot report](https://ethresear.ch/t/statement-regarding-the-public-report-on-the-analysis-of-minroot/16670)

**SNARK-based VDF collaboration (2021) and MinRoot (2022)**
- ZKProof blog (Nov 24, 2021): Protocol Labs, EF, Filecoin Foundation, Supranational, Microsoft Research and Electric Coin Company collaborate on a "practical SNARK-based VDF": Sloth-variant with fifth roots (x → x^{1/5}; cube avoided because Pallas/Vesta have a 3-order subgroup), proven with Halo 2 / Nova IVC; prover has "approximately a 94× advantage" over the evaluator; goal "factor of 10" cost/performance; CPU evaluator with handwritten assembly, GPU CUDA MSM/NTT, "initial feasibility research for an ASIC." All planned, no results. — [ZKProof, Practical SNARK-based VDF](https://zkproof.org/2021/11/24/practical-snark-based-vdf/)
- MinRoot paper (Khovratovich, Maller, Tiwari; ePrint 2022/1626, Nov 2022, SBC 2022): round function g(x_i,y_i,i) = ((x_i+y_i)^{(2p−1)/3}, x_i + i) over F_p² for 256-bit p (BLS12-381 / BN254 scalar-field orders; fifth root exponent (4p−3)/5 when p ≢ 1 mod 5); t ≈ 2^36 for 1 minute, 2^42 for 1 hour, 2^46 for 1 day; claim: "128 bits of multitarget VDF security," sequentiality margin σ(t) = t/2 (i.e., attacker at most 2x faster); ASIC assumptions ~1 ns per square/multiply, ~300 ns per iteration, ~3.3M iterations/s; Ethereum planned Nova as the recursive SNARK; bounties for parallel GCD, algebraic inversion, multi-processor evaluation. — [ePrint 2022/1626 PDF](https://eprint.iacr.org/2022/1626.pdf)

**MinRoot cryptanalysis and the pause (2023–2024)**
- EF-organized workshop, Lyon, April 28–30, 2023; report dated Sept 18, 2023 by Leurent, Mennink, Pietrzak, Rijmen with ~20 collaborators (Biryukov, Bünz, Canteaut, Dinur, Dodis, Dunkelman, Fisch, Komargodski, Heninger, Naya-Plasencia, Perrin, Rechberger, Segev, Stam, Tessaro, Wesolowski…). MinRoot params p = 2^254 + 2^32·0x224698fc094cf91b992d30ed + 1, ~2^40 rounds, ~254 squarings per root. Attack table (speedup / processors / memory): 32 / 2^128 / 2^128 (BSGS); 42 / 2^54.5; 20 / 2^48 / 2^59.5; 18 / 2^40; 12 / 2^36; 4.7 / 2^34; **20 / 2^29 / 2^40 (parallel smoothness test)**; 3.7 / 2^25 / 2^40 (serialized version succeeded in >99% of 1000 trials). "Some of our results clearly break the security claims of MinRoot" but "it is unclear whether they can be implemented in practice"; ~2^50 processors could communicate within one round; conclusion: computing a root is "not a sequential operation" in the parallel setting; no recommended field size ("further work is required"). — [MinRoot analysis report (EF PDF)](https://crypto.ethereum.org/events/minrootanalysis2023.pdf)
- EF Cryptography Research Team statement (Sept 18, 2023; Herold, Kadianakis, Khovratovich, Maller, Simkin, Sanso, Zapico, Zhang): design goal was c=2 max speedup; the attack (a "three-day effort by leading cryptanalysts") shows a 256-bit root is faster "using 2^25 processors and 2^40 memory"; the same parallelization assumption also fails for Sloth++ (2018) and VeeDo (2020); VDFs lack "tested design patterns and attack tools"; **"At present we do not recommend using VDFs within Ethereum."** Reply by burdges (Sept 20): Bernstein argued ≥4 years earlier that residue number systems give parallel speedups across all VDF designs; "An adversarial advantage of 2 never sounded realistic of course." — [ethresear.ch: Statement regarding the MinRoot report](https://ethresear.ch/t/statement-regarding-the-public-report-on-the-analysis-of-minroot/16670)
- CRYPTO 2024 full version (Biryukov, Fisch, Herold, Khovratovich, Leurent, Naya-Plasencia, Wesolowski, ePrint 2024/873): "an attacker with about 2^29 processors can compute the round function roughly 20 times faster than a legitimate user"; attacks reduce to parallel discrete log; VeeDo-size 128-bit prime needs ~2^13–2^14 processors and 2^40 memory; speed-of-light limit "at most 250 processors can communicate within one round," ~2^40 cores per machine under cooling constraints; **"this project has been put on hold following our results."** — [ePrint 2024/873](https://eprint.iacr.org/2024/873.pdf)

**What Ethereum uses today: RANDAO and its bias**
- Selfish Mixing (Nero_eth, July 10, 2023): each tail-end slot is a binary choice (reveal or miss), so k tail slots give 2^k outcomes; at 25% stake a two-tail-slot entity has ~70% chance of ≥10 slots in N_{t+2} vs ~8 expected; Lido had 8 consecutive tail slots twice (epochs 149818, 184869); "what-if" analysis, no claim of actual manipulation; VDFs are "the main solution" but "there are no concrete plans to implement this solution." — [ethresear.ch: Selfish Mixing and RANDAO Manipulation](https://ethresear.ch/t/selfish-mixing-and-randao-manipulation/16081)
- "Forking the RANDAO" (Nagy, Tapolcai, Ladóczki, Seres; ePrint 2025/037, Jan 2025): mainnet measurements "revealed no statistically significant traces of these attacks to date"; Lido "could have manipulated the RANDAO with selfish mixing 47 694 times" but missed a slot in only 3 of 737 four-tail-slot epochs; two ex-ante reorgs by Lido observed (epochs 192,420 and 313,291, gaining one slot each); forking + selfish mixing lets α = 41.95% get 50% of slots (vs 46.24% for selfish mixing alone); VDFs "eliminate the possibility of bias" but are "non-trivial to deploy" with "severe hardware requirements." — [ePrint 2025/037](https://eprint.iacr.org/2025/037.pdf)
- "RANDAO target slot attack" (Tapolcai et al., Feb 13, 2025; ePrint 2025/219): 33% colluding stake secures a chosen target slot with 99.5% success; the largest pool (α=28%) has a 65% chance of controlling any given slot with ~24 outcomes (~5 bits) to choose from per epoch; theoretical, no mainnet evidence. — [ethresear.ch: RANDAO target slot attack analysis](https://ethresear.ch/t/randao-target-slot-attack-analysis/21740)
- "Unpredictable RANDAO" (Titania Research, June 25, 2025): proposes committee BLS threshold shares via the 16-member FOCIL IL committee to cut attacker choice from 2^k to k+1; no VDF; disputed in replies by Seres and Shoup. — [ethresear.ch: Unpredictable RANDAO](https://ethresear.ch/t/unpredictable-randao/22666)
- EIP-8321 "Hash-Chain RANDAO" (Wedderburn, Wagner, Wambsgans, Drake, Coratger; created 2026-07-05, Draft): replaces BLS reveals with blake3 hash-chain commit-reveal for post-quantum reasons; "bias stays at one bit per proposer"; proposer duties for epoch E drawn from the mix at end of epoch E − MIN_SEED_LOOKAHEAD − 1; no mention of VDFs. — [EIP-8321](https://eips.ethereum.org/EIPS/eip-8321)
- SSS-based alternative (Son, Quynh, Minh; arXiv 2403.09541, ~late 2023): cites a Buterin claim that 36% stake could control the network; proposes Shamir-share RANDAO rather than a VDF, noting the VDF "hardware drawback." — [arXiv 2403.09541](https://arxiv.org/html/2403.09541v1)

### Inferences
- The "fast enough, not fastest" strategy (Drake, 2019) depended on bounding A_max via open hardware; the FPGA contest (50 → 25.2 ns/sq on 1024-bit) and the 2 ns ASIC target implied a >10x gap between FPGA and ASIC, which is why the ASIC was considered essential. No evidence of an RSA ASIC tapeout was found.
- The pivot to MinRoot traded the RSA trusted-setup problem for an untested sequentiality assumption; the cryptanalysis showed the c=2 bound was unrealistic by an order of magnitude, which is the proximate reason for the pause. As of October 2026 there is no sign (EIP-8321, Titania proposal, beam/lean-chain discourse) that VDFs are back on Ethereum's roadmap.
- RANDAO's practical bias is small in expectation (sub-1% excess slots for α ≤ 0.2 per Titania's summary of Alpturer–Weinberg) but large in targeted settings (5 bits for a 28% staker), which matters for applications that read `prevrandao`.

### Gaps
- I could not find a primary source for the final VDF Alliance Round 3 (Jan 2020) results page; only Jane Street's blog describes the outcome.
- No public evidence of the Supranational RSA-2048 evaluator ASIC having been fabricated; the wiki page was last updated July 2019.
- No Justin Drake / EF statement after Sept 2023 explicitly revisiting VDFs; the "paused" status is inferred from the Sept 2023 statement and the CRYPTO 2024 paper's "put on hold."

## Key Question 3: Other chains that shipped or seriously prototyped a VDF for randomness

### Takeaway
Tezos is the one other L1 running a true VDF for randomness (class-group Wesolowski, VDF_DIFFICULTY = 2.4×10^9, since Kathmandu Sept 2022, using Chia's library ported to OCaml, with RANDAO fallback). Harmony implemented a VRF+VDF "DRG" (Wesolowski class group, Go, difficulty 50,000 ≈ 100 s) but only VRF has a documented mainnet activation epoch (631, July 2021). Autonomys/Subspace (mainnet Nov 2024) uses AES-128 repeated encryption (~183M iterations/s, 8 checkpoints, "not technically a VDF"). Filecoin, Dfinity, Mina, Polkadot and Solana do not use VDFs for randomness.

### Cited Findings

**Tezos (live, since Sept 2022)**
- Nomadic Labs (Nov 21, 2022): VDF phase added after RANDAO to defeat the "last revealer's advantage"; announced July 2022 in the Kathmandu proposal and activated September 2022; seed = hash(RANDAO output, VDF solution), falling back to RANDAO alone if no valid VDF is submitted; first baker to submit a correct solution gets a tip; implementation adapted from "ocaml-chia-vdf" (Chia's library); "Tezos is currently the only blockchain using a VDF for randomness generation"; Tezos uses a software VDF "because no hardware VDF exists yet"; Tezos and Ethereum are advisory partners in the VDF Alliance. — [Nomadic Labs, Improving Randomness in Tezos with VDFs](https://research-development.nomadic-labs.com/verifiable-delay-functions.html)
- Octez docs (Rio): VDF "based on class groups and using Wesolowski proofs"; `VDF_DIFFICULTY = 2,400,000,000`; `NONCE_REVELATION_THRESHOLD = 400` blocks; `BLOCKS_PER_COMMITMENT = 112`; the discriminant is "a prime number defining the class group" derived from the cycle n−1 seed; "Any party can compute a VDF solution and publish it on-chain together with a proof of correctness"; "To ensure liveness, we fallback to RANDAO entropy if no VDF output was published and verified on-chain." — [Octez docs: Randomness generation (Rio)](https://octez.tezos.com/docs/rio/randomness_generation.html); [Octez docs (alpha)](https://octez.tezos.com/docs/alpha/randomness_generation.html)
- OCaml library `class_group_vdf` 0.0.4: `discriminant_size_bytes = 128` (i.e., 1024-bit discriminant), `form_size_bytes = 100`, `type difficulty = int64`. — [class_group_vdf source](https://ocaml.org/p/class_group_vdf/0.0.4/src/class_group_vdf/vdf_self_contained.ml.html)
- Rio protocol (2025) lowered mainnet `BLOCKS_PER_CYCLE` from 30720 (~2.8 days) to 10800 (~1 day) with 8-second blocks; no randomness changes listed. — [Octez docs: Rio protocol](https://octez.tezos.com/docs/protocols/022_rio.html)
- Original design issue (Raphael Toledo, edited Apr 19, 2022): RANDAO output "will be the input to a VDF with security and difficulty parameters large enough to prevent any party from computing the randomness seed" before the reveal cutoff; MR 5064. — [Tezos GitLab issue #2844](https://gitlab.com/tezos/tezos/-/issues/2844)

**Harmony (VDF code present; mainnet activation unconfirmed)**
- Design (Dec 5, 2018 forum post by rongjian): DRG protocol = leader collects validator VRFs, XORs into pRnd, BFT-commits it, computes Rnd = VDF(pRnd, T) with T "set algorithmically such that the randomness can only be computed after k blocks"; described as similar to Unicorn. — [Harmony forum: Unbiasable randomness with VRF and VDF](https://talk.harmony.one/t/unbiasable-randomness-generation-with-vrf-and-vdf/)
- Harmony docs: DRG runs once per epoch; after >2/3 of validators submit VRFs the leader XORs them into pRnd; "The leader computes Rnd = VDF(pRnd, T)"; no construction or numeric T/k given; no statement about production status. — [Harmony docs: Randomness](https://docs.harmony.one/home/general/technology/randomness)
- `harmony-one/vdf`: "The first go implementation of verifiable delay function (VDF)," "based on Benjamin Wesolowski's paper," class groups ("only 2048 integer size for class group variables are supported now"), "the VDF used in Harmony Project"; 38 commits, MIT. — [harmony-one/vdf GitHub](https://github.com/harmony-one/vdf)
- Node source (main branch, fetched Oct 16, 2026): `mainnetVdfDifficulty = 50000 // This takes about 100s to finish the vdf` ([mainnet.go](https://raw.githubusercontent.com/harmony-one/harmony/main/internal/configs/sharding/mainnet.go)); `GenerateVdfAndProof` derives the seed by XORing VRFs, runs `vdf_go.New(shard.Schedule.VdfDifficulty(), seed)` in a goroutine and sends 548 bytes to `RndChannel` ("The first 516 bytes are the VDF+proof and the last 32 bytes are XORed VRF as seed"); `ValidateVdfAndProof` reads `headerObj.Vdf()` ([consensus_v2.go](https://raw.githubusercontent.com/harmony-one/harmony/main/consensus/consensus_v2.go)); `WaitForNewRandomness` appends VDF outputs to `pendingRnds` and `GetNextRnd` pops them ([consensus_service.go](https://raw.githubusercontent.com/harmony-one/harmony/main/consensus/consensus_service.go)). Chain config has `VRFEpoch: big.NewInt(631), // Around Wed July 7th 2021` and **no `VDFEpoch`** field ([config.go](https://raw.githubusercontent.com/harmony-one/harmony/main/internal/params/config.go)).
- The VRF is generated in block proposal only `if node.Blockchain().Config().IsVRF(header.Epoch())`; the fetched excerpt of `node_newblock.go` contained no VDF call. — [harmony node_newblock.go](https://github.com/harmony-one/harmony/blob/main/node/node_newblock.go)
- Academic benchmark (Avarikioti et al., Aug 2026) of the Harmony Wesolowski implementation: difficulty 5,000 → 14.966 s compute / 736 ms verify; ~60 min compute (3677.8 s) → 782 ms verify; proof "consistently below 516 bytes." — [arXiv 2608.13271](https://arxiv.org/pdf/2608.13271)
- SoK (Raikwar & Gligoroski, 2022) lists Harmony (VRF+VDF) as a hybrid protocol with no deployment status, and makes "no claim that any VDF-based beacon is deployed." — [arXiv 2205.13333](https://arxiv.org/pdf/2205.13333)

**Autonomys / Subspace (AES "Proof-of-Time", live Nov 2024)**
- Delay function is "repeated AES-128 encryption"; footnote: AES is "not technically a VDF" because encryption and decryption cost the same, but it "can work as a VDF in practice by parallelizing verification"; ~183 million iterations per slot targeting ~1 s on high-end CPUs; 8 uniformly spaced 128-bit checkpoints let verifiers check in parallel "~7 times faster" using "~4 times less power"; "A single honest timekeeper is sufficient"; entropy injection every 50 blocks (~5 min) so "Speed gains are not cumulative over time"; lag parameter 4 slots; joint study with Supranational found no "significant speedup over the best AES implementation, even with an ASIC." — [Autonomys Academy: Proof-of-Time](https://academy.autonomys.xyz/autonomys-network/consensus/proof-of-time); [Subspace blog, Securing Dilithium with Proof-of-Time (Oct 24, 2023)](https://medium.com/subspace-network/securing-dilithium-with-proof-of-time-26a82aa5b7e0)

- Mainnet launched November 6, 2024 with a PoT seed ceremony using Bitcoin block #869146 as external entropy. — [Autonomys forum: Mainnet launched](https://forum.autonomys.xyz/t/autonomys-mainnet-launched-by-the-subspace-foundation/4541)

**Chains that considered or do not use VDFs**
- Filecoin: randomness comes from the drand beacon (BLS signature hashed with blake2b) plus VRF-chain tickets; the spec does not mention VDFs. — [Filecoin spec: Randomness](https://spec.filecoin.io/algorithms/crypto/randomness/). Protocol Labs co-funded the EF VDF research in 2019 ("Filecoin and Ethereum are both exploring the use of VDFs"). — [Protocol Labs blog](https://pl.xyz/blog/collaboration-on-vdfs)
- Dfinity: random beacon is a unique, deterministic threshold BLS signature stream (VRF), no VDF. — [arXiv 1805.04548](https://arxiv.org/abs/1805.04548)
- Mina: Ouroboros Samasika slot leadership by VRF; 7,140 slots per epoch; no VDF mentioned. — [Mina blog: What is Ouroboros Samasika](https://minaprotocol.com/blog/what-is-ouroboros-samasika)
- Polkadot: BABE VRF (Ouroboros Praos-style); its docs say a VDF "likely requires specialized ASIC devices" and "involves significant costs without direct incentives." — [Polkadot docs: Randomness](https://docs.polkadot.com/reference/parachains/randomness/)
- Solana: PoH is Solana's "application-specific VDF" (a hash chain) but "The PoH chain therefore does not serve as a good source of randomness," and verification time is proportional to generation time (run across a 4000-core GPU). — [Anza docs: Synchronization](https://docs.anza.xyz/consensus/synchronization)

- ethresear.ch "Nakamoto consensus with VDF and VRF" (jieyilong, June 2019): Pietrzak squaring with difficulty inversely proportional to stake; only a "pseudo-VDF" prototype (Vixify, 2020) followed. — [ethresear.ch thread](https://ethresear.ch/t/nakamoto-consensus-with-vdf-and-vrf/5671)

### Inferences
- Tezos's design (VDF output hashed with RANDAO, RANDAO fallback) is the cleanest production example of the "collect entropy, then slow function" pattern; its 2.4×10^9 squarings on a 1024-bit class group with a ~1-day cycle leaves ample margin, and the "first correct submitter gets a tip" model means liveness depends on altruistic/tipped bakers.
- Harmony: VDF code paths, a mainnet difficulty constant, and a header field exist, but the only gated activation flag is for VRF (epoch 631). Given the absence of a VDF epoch flag and no post-2021 documentation, the safest reading is that Harmony's VDF is either latent or ungated; I could not confirm it produces on-chain randomness today.

- Tezos: no published figure for wall-clock time of 2.4×10^9 squarings on current hardware, nor the number of bakers submitting VDF solutions per cycle.
- Autonomys: no post-launch disclosure of timekeeper counts or measured ASIC speedups.

## Key Question 4: StarkWare VeeDo (STARK-proven VDF, 2020)

### Takeaway
VeeDo launched on Ethereum mainnet as a proof-of-concept on June 23, 2020: an algebraic delay function (iterated cubic-root-finding over a 126-bit prime, ~634 ns/iteration, 10·2^25−1 iterations ≈ 3.5 min), STARK-proven off-chain and verified by an on-chain contract, feeding a randomness beacon seeded every 820 blocks. Its core sequentiality assumption (no parallel speedup of root extraction) was shown false in the 2023 EF analysis and CRYPTO 2024 paper; there is no evidence the service is still operated, and StarkWare has not published updates since 2020.

### Cited Findings
- "Presenting VeeDo" (StarkWare, June 23, 2020): STARK-based VDF service "now live on Mainnet"; each iteration "finds a root of a low-degree (cubic) polynomial modulo a prime p," PoC uses a 126-bit prime; root-finding "roughly 42x harder than the inverse direction"; iterations 10·2^25−1 at "~634 ns" each → "approximately 3.5-minute" delay; a block picked every 820 blocks (~3 hours) with randomness on-chain ~20 minutes later; beacon contract 0xC405fF8406bFfBc97bc46a1Ae5ECe55112DcF8f4, verifier 0x5a6a37b41865eb940c5dd4ffe162e53b7ee22090; "no guarantees on uptime, nor on the service's longevity"; claimed GPUs/FPGAs have no latency advantage over a 64-bit CPU (white paper promised); uses pitched: randomness beacon (vs Chainlink/Keep trust assumptions), timelocks, hardware-leveling PoW. — [StarkWare Medium: Presenting VeeDo](https://medium.com/starkware/presenting-veedo-e4bbff77c7ae)
- StarkWare Labs page describes VeeDo only as combining "STARKs and VDF" for "trustless randomness" and timelocks; no status or date. — [starkware.co VeeDo page](https://starkware.co/?p=2669)
- a16z crypto (Oct 2022) describes Starkware's work as a "proof-of-concept VDF-based beacon" using SNARK-based VDFs, "not presented as a deployed chain." — [a16z crypto](https://a16zcrypto.com/posts/article/public-randomness-and-randomness-beacons/)
- EF statement (Sept 2023): the parallelization assumption "was also shown to fail for Sloth++ (2018) and VeeDo (StarkWare, 2020)." — [ethresear.ch EF statement](https://ethresear.ch/t/statement-regarding-the-public-report-on-the-analysis-of-minroot/16670)
- CRYPTO 2024 paper: for a 128-bit prime "(as in Veedo)" the smoothness attack needs ~2^13 processors (2^14 in Table 2) and 2^40 memory; "The previous algorithms break the sequentiality of several VDF constructions," naming VeeDo and Sloth++. — [ePrint 2024/873](https://eprint.iacr.org/2024/873.pdf)
- MinRoot paper (Nov 2022) positioned itself as "a strict improvement over competitors VeeDo and Sloth++." — [ePrint 2022/1626](https://eprint.iacr.org/2022/1626)
- Earlier context (Oct 2018 session notes): StarkWare's view then was that STARKs "do not currently appear to be an optimal VDF solution"; Drake proposed competitions for iterated PRFs suitable for STARK-based VDFs. — [notes.ethereum.org](https://notes.ethereum.org/b8DsLbLcRmKHlWAXEXt_Rw)
- SoK (2022) lists VeeDo (STARK+VDF) as a smart-contract DRB with a GitHub link and no deployment status. — [arXiv 2205.13333](https://arxiv.org/pdf/2205.13333)

### Inferences
- VeeDo's lesson is the same as MinRoot's: a STARK makes verification cheap and trustless, but the delay function underneath (small-field algebraic root extraction) is exactly the class the cryptanalysts broke. A STARK-proven RSA/class-group squaring chain would avoid that, at much higher proving cost.
- The 126-bit prime is also far below MinRoot's 256-bit choice; the CRYPTO 2024 estimate (~2^13–2^14 processors) makes a VeeDo-scale attack much closer to practical than the MinRoot one.

### Gaps
- No StarkWare post-2020 update, uptime data, gas cost, or STARK proof size for VeeDo was found; I could not confirm whether the beacon contract ever received proofs after 2020 (would require an Etherscan query).
- The promised VeeDo white paper with hardware analysis was not located.

## Key Question 5: Unicorn / sloth (Lenstra & Wesolowski 2015) and deployments

### Takeaway
Sloth (iterated modular square roots mod a prime p ≡ 3 mod 4, verification ≥ log2(p)−2 times faster than evaluation) and the Unicorn beacon (collect public entropy for ≤2 minutes, commit, then run ~10 minutes of sloth) are the conceptual origin of "collect entropy then slow function." The only implementation the authors reported running was "trx" (trustworthy random elliptic-curve generation); later academic beacons (Breeding Unicorns 2020, Random UChile's CLCERT) prototyped sloth/VDFs but none became a production blockchain beacon.

### Cited Findings
- Sloth: pick prime p ≡ 3 mod 4, p ≥ 2^{2k}; iterate a permutation τ = ρ∘σ ℓ times; square roots via exponent (p+1)/4; verification "already at least log2(p) − 2 times faster than the computation"; Table 1 (10-minute computation, swapping-neighbors σ): 31,000,000 iterations for n=256 (7.7 s verify), 6,750,000 for 512 (2.7 s), 1,100,000 for 1024 (0.84 s), 155,000 for 2048 (0.33 s), 23,600 for 4096 (0.15 s) vs 600 s generation; checkpointing speeds verification by a further factor. — [ePrint 2015/366 PDF](https://eprint.iacr.org/2015/366.pdf)
- Unicorn protocol: announce collection window at t−2; collect public data (e.g., hashtag tweets) from t−1 to t0 (window "should not be more than two minutes before t0"); at t0 publish s0 and run sloth on s0‖s1 (s1 = camera picture at t0); publish commitment "almost instantaneously"; later publish hash, witness, s1; anyone verifies. Security lower bound uses two minutes of sloth; overclocking to ~9 GHz "would lead to a wall-clock time guarantee of about three minutes." Last contributor "cannot knowingly influence the outcome." — [ePrint 2015/366 PDF](https://eprint.iacr.org/2015/366.pdf)
- Deployment: "trx has recently been implemented" on a desktop, producing random curve parameters at k ∈ {128,192,256}, "less than two hours for k = 128 to about a week for k = 256," with a camera at a physically secure location as randomness source; random-sample voting and a random beacon are proposed, not deployed. — [ePrint 2015/366 PDF](https://eprint.iacr.org/2015/366.pdf); abstract — [ePrint 2015/366](https://eprint.iacr.org/2015/366/20151204:121121)
- "Breeding Unicorns" (Dharanikota et al., PLOS ONE, Apr 28, 2020): open-source beacon (github.com/randomchain/randbeacon) using sloth with tunable prime bits and iterations (tests at 512/1024 prime bits, 1024/2048 iterations); Ethereum lottery on a private testnet; no public live beacon URL or run duration; lessons: publish inputs/commitments early; users can only trust outputs if the delay cannot be computed faster than the input-to-commitment gap; on-chain verification is costly (EIP-198 modexp helps). — [PLOS ONE PDF](https://vbn.aau.dk/ws/files/404706842/pone.0232261.pdf)
- Random UChile (CLCERT) `clcert/vdf` repo: "explore proposals and implementations of VDFs, with the goal of using it in Random UChile's randomness beacon" (student project CC5905); 46 commits; no confirmation of production use. — [clcert/vdf GitHub](https://www.github.com/clcert/vdf)
- SoK (2022): Unicorn listed as VDF-based DRB using sloth, no deployment stated; "the nodes having the most efficient (fastest) processors can always learn the beacon outputs before the other participating nodes." — [arXiv 2205.13333](https://arxiv.org/pdf/2205.13333)
- Harmony's 2018 design explicitly described itself as "similar to the 'Unicorn' protocol." — [Harmony forum](https://talk.harmony.one/t/unbiasable-randomness-generation-with-vrf-and-vdf/)
- Tezos's RANDAO→VDF and Ethereum's RANDAO→VDF are the same pattern (see Q2, Q3). — [Nomadic Labs](https://research-development.nomadic-labs.com/verifiable-delay-functions.html); [ethresear.ch Minimal VDF beacon](https://ethresear.ch/t/minimal-vdf-randomness-beacon/3566)

### Inferences
- Sloth's verification advantage is only ~log p (hundreds to a few thousand x), far weaker than Wesolowski/Pietrzak's exponential gap; this is why no blockchain adopted raw sloth, and why StarkWare wrapped a sloth-like function in a STARK (VeeDo) and the EF wrapped a sloth-variant in Nova (MinRoot).
- Sloth++/VeeDo/MinRoot all inherit sloth's "root extraction in a prime field" core; the 2023–2024 cryptanalysis therefore applies to the whole lineage, not just MinRoot.

### Gaps
- I found no evidence that trx or any Unicorn beacon is currently running; the 2018 journal version (Inderscience IJACT) was not fetched.
- Random UChile's production beacon design (whether it ended up using a VDF) was not verified.

## Key Question 6: 2024–2026 developments and expert consensus on RSA vs class-group VDFs

### Takeaway
2024–2026 brought no new production VDF beacon beyond Autonomys's AES PoT (Nov 2024). Research shifted to (a) cheap on-chain verification (Pietrzak RSA-2048 at ~1.8–2.6M gas with 5–7 KB proofs, Jan 2025; Seedy hackathon raffle), (b) negative results (VDFs impossible in the ROM, CRYPTO 2025; algebraic VDFs broken, CRYPTO 2024), (c) post-quantum lattice VDFs (Papercraft, S&P 2025: 6-minute computation verified in 7 s), and (d) economic security (Shang–Chen, Apr 2026: few-second delays are economically insecure). Consensus: only groups-of-unknown-order squaring (RSA or class group) is deployable; class groups avoid trusted setup but need larger discriminants (~1208-bit per Dobson–Galbraith–Smith) than Chia/Tezos's 1024 bits; both are quantum-breakable; the adversary speedup bound must be assumed ≫2. *(Corrected 2026-10-17: an earlier version added "Boneh et al. suggest s=100"; in the survey s is the number of processors used to speed up proof generation, not an adversary speedup. See `sequential_hash_hardware.md` Q6.)*

### Cited Findings

**New deployments / applications**
- Autonomys mainnet with AES-based PoT launched Nov 6, 2024 (see Q3). — [Autonomys forum](https://forum.autonomys.xyz/t/autonomys-mainnet-launched-by-the-subspace-foundation/4541)
- Chia ASIC timelord community rollout completed June 2024 (see Q1). — [Chia blog](https://www.chia.net/2024/06/10/global-expansion-of-chia-network-security-with-successful-asic-timelord-rollout/)
- Pietrzak VDF on-chain verification study (Lee, Gee, Lee; Korea University/Tokamak; Jan 23, 2025): RSA-2048 with δ=9 costs ~1.82M gas (τ=20) to ~2.60M gas (τ=25) with proofs of "5.38 to 7.25 KB" (vs ~40 KB previously expected); 3072-bit: ~3.50–4.96M gas, 7.13–9.63 KB; Wesolowski rejected on-chain because hash-to-prime via Miller–Rabin costs ~21,446 gas per candidate with up to ~5,939 candidates; est. $33.9–$136.6 per verification at τ=25 (ETH $2,600, 5–20 gwei); "somewhat expensive but may be acceptable for security-critical operations that are not executed frequently," better on L2. — [arXiv 2405.06498v5](https://arxiv.org/html/2405.06498v5)
- Seedy (ETHGlobal Taipei hackathon; won Celo L2 pool prize): Pietrzak verifier (SeedyVerifier.sol, EIP-198 modexp, BigNumbers.sol) + coordinator storing keccak256(y) + Raffle.sol consumer; demo only, no mainnet address given. — [ETHGlobal showcase: Seedy](https://ethglobal.com/showcase/seedy-sn1hq)
- Neodyme (Nov 2022) sketched a class-group Wesolowski on-chain RNG for Solana but found generating a 1024-bit prime needs hundreds–thousands of transactions (1.4M CU limit; ~11,000 CU per 1024-bit remainder); scheme "not been subjected to due scrutiny"; "Chia is the only major project using VDFs in practice." — [Neodyme](https://neodyme.io/en/blog/secure-randomness-part-2/)
- "Slow and Steady" (Avarikioti, Karakostas, Kreder, Shastry; arXiv Aug 13, 2026): proposes VDF-delayed transaction generation as an MEV defense; recommends delay = 2× safety parameter (~60 min Bitcoin, ~30 min Ethereum); "Wesolowski's VDF is a prime choice"; research proposal, no deployment; notes VDFs "lack rigorous theoretical lower bounds." — [arXiv 2608.13271](https://arxiv.org/pdf/2608.13271)
- Lenstra-style "Unbiasable RNG" design (HackMD @Zergity, undated): VDF evaluators commit-then-reveal with required evaluation length T_e ≥ InputAge × MaxSpeed/MinSpeed; design doc, not shipped. — [HackMD UnbiasableRNG](https://hackmd.io/@Zergity/UnbiasableRNG)

**Cryptanalysis and theory (2024–2026)**
- CRYPTO 2024: algebraic VDFs (Sloth++, VeeDo, MinRoot) broken in the parallel model; MinRoot ~20x with 2^29 processors; "this project has been put on hold." — [ePrint 2024/873](https://eprint.iacr.org/2024/873.pdf)
- CRYPTO 2025 (Guan, Riazanov, Yuan, EPFL; ePrint 2024/766, revised to July 12, 2026): "VDFs do not exist in the random oracle model," ruling out black-box constructions from OWFs, OWPs and CRHFs; only known ROM constructions assume hardness of repeated squaring. — [ePrint 2024/766](https://eprint.iacr.org/2024/766); [Cornell theory seminar, Aug 27, 2025](https://www.cs.cornell.edu/events/theory-seminar/breaking-verifiable-delay-functions-random-oracle-model)
- Papercraft (Osadnik, Kaviani, Cini, Lai, Malavolta; IEEE S&P 2025; ePrint 2025/879 revised June 23, 2026): first implementable lattice-based VDF, "plausibly post-quantum secure," verifies "a computation of almost 6 minutes … in just 7 seconds." — [ePrint 2025/879](https://eprint.iacr.org/2025/879)
- Economic security of VDF beacons (Shang & Chen, HKUST; arXiv 2604.04744, Apr 6, 2026, targeting CCS Nov 2026): models a rational attacker with speedup δ ≥ 1 as an optimal-stopping problem; "many proposed VDF delays, on the order of a few seconds, are economically insecure under plausible conditions"; proposes Economically Secure Delay Parameters; Case Study 1 is a "VDF Beacon with 2–5 Second Delay." — [arXiv 2604.04744](https://arxiv.org/html/2604.04744v1)

**RSA vs class groups: parameters and expert views**
- Wesolowski (2018): RSA group (Z/NZ)×/{±1} or class group Cl(d) of an imaginary quadratic field with d a negative prime (odd class number); soundness relies on a new root-finding assumption; proof is one group element, verification ~two small exponentiations. — [ePrint 2018/623](https://eprint.iacr.org/2018/623.pdf)
- Boneh–Bünz–Fisch survey: Pietrzak proof log2 T elements, O(√T) proving, low-order assumption; Wesolowski one element, O(T) proving, adaptive-root assumption ("potentially a stronger assumption"); "Both provers parallelize well … Taking s = 100 seems reasonable in practice" (s = processors for proof generation, not an attacker speedup; corrected 2026-10-17); Shor breaks both. — [Stanford VDF survey](https://crypto.stanford.edu/~dabo/pubs/papers/VDFsurvey.pdf)
- Dobson–Galbraith–Smith "Trustless unknown-order groups" (ePrint 2020/196, rev. Mar 2022): "current parameters do not meet claimed security levels"; against the L|Δ|(1/2) class-group order algorithm (Hafner–McCurley) "a much larger negative prime discriminant of around 1208 bits would be required"; conjecture genus-3 hyperelliptic Jacobians give shorter keys. — [ePrint 2020/196](https://eprint.iacr.org/2020/196.pdf)
- Chia's rationale for class groups: no trusted setup, at the cost of less-tested code and less-known optimizations. — [Chia docs: Proof of Time](https://docs.chia.net/proof-of-time)
- Tezos docs: class groups chosen as the trustless option "alongside MPC-generated RSA groups"; Wesolowski shorter proofs but stronger assumption than Pietrzak. — [Octez docs](https://octez.tezos.com/docs/rio/randomness_generation.html)
- EF (2023): RSA needed a trusted setup whose MPC was broken in audit; MinRoot replaced it; now "do not recommend using VDFs within Ethereum." — [ethresear.ch EF statement](https://ethresear.ch/t/statement-regarding-the-public-report-on-the-analysis-of-minroot/16670)
- burdges (Sept 2023): "An adversarial advantage of 2 never sounded realistic of course"; asks whether results rule out protocols assuming 10x or 100x. — [ethresear.ch EF statement thread](https://ethresear.ch/t/statement-regarding-the-public-report-on-the-analysis-of-minroot/16670)
- Neodyme (with Wesolowski/Cohen input): Mersenne-prime discriminants "should never be used" (Belabas, Kleinjung, Sanso, Wesolowski); root-finding and time-lock assumptions "have received relatively little scrutiny"; a simple quantum-resistant VDF "remains an open problem." — [Neodyme](https://neodyme.io/en/blog/secure-randomness-part-2/)
- Supranational hardware: Chia ASIC timelords are the only shipped VDF ASICs found (Q1); Supranational's 2022 AES study for Subspace concluded no significant ASIC speedup over AES-NI (Q3); the 2019 RSA-2048 evaluator ASIC design shows no evidence of fabrication (Q2).
- a16z (Oct 2022): VDF beacons are "a promising new direction" that "has seen some practical deployment" but "we still lack any standard DRB that provides high security." — [a16z crypto](https://a16zcrypto.com/posts/article/public-randomness-and-randomness-beacons/)
- SoK (2022): VDF-based DRBs "depend on the new security assumptions on sequential computation," which are "not well studied and understood." — [arXiv 2205.13333](https://arxiv.org/pdf/2205.13333)

### Inferences
- The field's working consensus by 2026: (1) field-based/algebraic VDFs are out; (2) group-of-unknown-order squaring is the only deployable primitive, with RSA requiring an MPC that has proven hard to get right and class groups requiring discriminants above what Chia/Tezos use plus per-epoch rotation; (3) assume adversarial speedup well above 2x when sizing delays (no source fixes a number; the earlier "Boneh et al. s=100" here was a misreading, corrected 2026-10-17, see `sequential_hash_hardware.md`); (4) lattice VDFs exist but are minutes-scale and unproven at protocol scale.
- The SNARK-wrapped direction (VeeDo, Nova/MinRoot, Seedy's EVM Pietrzak verifier) is alive for verification cost, but the only SNARK-wrapped designs that would survive the 2024 cryptanalysis are ones proving RSA/class-group squaring, which none of the shipped systems did.

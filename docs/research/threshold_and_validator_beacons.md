# Threshold-cryptography beacons and validator-native randomness (no VDF) — status as of 2026-10-16

Scope note: these notes cover every non-VDF design in the assignment. Each section ends with an explicit **trust-model classification** (permissioned validator set / fixed committee / external operator) because the reader wants an operatorless, permissionless PoW L1. Headline conclusion up front: **every unbiasable-and-unpredictable design found here depends on a known, enumerable signer set that runs a DKG (drand, ICP, Aptos, Sui, Flow). Every validator-native design that avoids a DKG (Algorand, Cardano Praos, Ethereum RANDAO, Polkadot BABE) is unpredictable-ish but biasable by block withholding/grinding, with the bias bounded only by the adversary's stake share.** No source described a threshold beacon running on a permissionless PoW chain without an operator set.

Several pages could not be fetched (AIP-41 text on GitHub, eth2book RANDAO chapter, Flow forum "secure RNG" post, docs.sui.io random-beacon concept page, Sui randomness-onchain .md mirror); those gaps are flagged in the relevant sections. Web search budget for this session was exhausted near the end, so a few follow-ups (Sui mainnet protocol-version confirmation beyond the newsletter, Aptos mainnet enablement date) rest on single sources.

## Q1. drand / League of Entropy (threshold BLS beacon)

### Takeaway
drand is a permissioned consortium beacon (League of Entropy, ~15–17 orgs, 22–23 mainnet nodes, threshold 12-of-22 on quicknet as of Oct 2023) producing BLS12-381 threshold signatures every 3 s (quicknet, unchained, 48-byte G1 sig) or 30 s (legacy default chain, chained, 96-byte G2 sig). BLS uniqueness makes the output unbiasable even if all operators collude; unpredictability holds only if fewer than t operators collude; availability requires t online. On-chain verification is a 2-pairing check: ~130–140k gas on Ethereum post-Pectra (EIP-2537), ~159k gas via the BN254 "evmnet" beacon on chains without BLS12-381 precompiles.

### Cited Findings

**Networks, parameters, dates**
- Three LoE networks: `default` (chained, launched 2020, 30 s period, signatures on G2, not tlock-compatible); `quicknet` (unchained, launched 2023, 3 s period, signatures on G1, tlock-compatible); `evmnet` (unchained, launched 2024, 3 s period, signatures on G1, **BN254 curve** so EVM precompiles can verify) — [drand.love/about](https://www.drand.love/about)
- quicknet mainnet launched 2023-08-23 (testnet quicknet-t 2023-07-13); GA announced 2023-10-16; one beacon every 3 s vs 30 s legacy; nodes stated as 23 in one place and 22 in another; **threshold 12 of 22**, "should rise as members join"; signature on G1 = **48 bytes**, group public key on G2 = **96 bytes**; chain hash `52db9ba70e0cc0f6eaf7803dd07447a1f5477735fd3f661792ba94600c84e971`; scheme ID `bls-unchained-g1-rfc9380`; legacy default chain "might be deprecated within ~18 months, nothing final"; predecessor `fastnet` (launched 2023-03-01) sunset because its G1 sigs were not RFC 9380-compliant; Filecoin-based "draffle" lottery cited as an on-chain consumer — [drand blog: quicknet is live](https://docs.drand.love/blog/2023/10/16/quicknet-is-live)
- RWC 2025 slides characterize the (default) drand network as "threshold BLS on BLS12-381, 20 nodes, t=11, 256 bits every 30 seconds, launched 2019" — [RWC 2025 slides #69](https://iacr.org/submit/files/slides/2025/rwc/rwc2025/69/69_slides.pdf)
- League of Entropy page (modified 2026-03-05) lists **17 mainnet member logos** (Cloudflare, Ethereum Foundation, Kudelski Security, QRL, Automata Network, University of Chile, ChainSafe, C4DT, DIA, EPFL DEDIS, Protocol Labs, Emerald Onion, UCL, IPFS Force, Lucerne University of Applied Sciences and Arts, Chengdu University of Information Technology, Polytechnic University of Catalonia) but the text says "a coalition of 15 independent organizations"; alumni: IC3, Tierion, ZenGo, cLabs, PTisp, ZKV; no node count or threshold stated — [drand.love/loe](https://drand.love/loe)
- History: dev began 2017 at EPFL DEDIS; LoE launched 2019 (Cloudflare Crypto Week); default mainnet relaunched as v1.0 Aug 2020 with 14 partners; Randamu became steward in 2024 — [drand.love/about](https://www.drand.love/about)

**Cryptography and chained vs unchained**
- Curve BLS12-381, pairing e: G1×G2→GT. `pedersen-bls-chained`/`pedersen-bls-unchained`: sigs in G2 (96 B), pubkeys in G1 (48 B). `bls-unchained-on-g1` (v1.5.0+): sigs in G1, pubkeys in G2. Threshold t = f+1 with f < n malicious; Shamir over Z_p; Pedersen DKG = n parallel Feldman VSS with complaint/reveal; partial sig σ_i = s_i·H(m); full sig via Lagrange interpolation of t partials. **Chained: m = H(r ‖ σ_{r−1}); unchained: m = H(r).** Random output = H(σ_r). Verification: e(H(m), S) = e(σ, g2). Signatures are deterministic — "any two signatures on the same message under the same key are identical" (this is the uniqueness property) — [drand cryptography docs](https://docs.drand.love/docs/cryptography/)
- Unchained mode: "each beacon is independent of previous ones, so a beacon can be verified statelessly"; because the future message H(r) is predictable, unchained mode "enables timelock encryption in production"; tlock service was security-audited — [drand blog: quicknet is live](https://docs.drand.love/blog/2023/10/16/quicknet-is-live)
- Independent Rust verifier (Ideal Labs, 2024) for quicknet: randomness = SHA-256(signature); message = SHA-256(big-endian round number) (prev_sig empty); check e(sig, g2) == e(H(m), pk) with sigs in G1, keys in G2; uses `w3f_bls`/arkworks — [verifier.rs mirror](https://www.bittensor.com/code/raw/pallets/drand/src/verifier.rs)

**Security model (who must be honest)**
- t nodes must be online and honest to produce each beacon. DKG requires malicious parties strictly < 50% of nodes; analysis assumes threshold > 50% (50%+1). **If ≥ t nodes are malicious, the attacker can derive the entire future chain (unpredictability lost) but "randomness remains unbiasable: the attacker cannot change the output in any way."** With < t malicious, no information about future beacons. An active adversary who DoSes ~N/2 nodes while holding the final share can decide whether/when to release a beacon and use it before the rest of the network sees it. Network is explicitly "permissioned"; all participants must know all other public keys before DKG; group creation uses a coordinator assumed fully honest at setup (TOFU); no reliable broadcast channel (malicious dealer can split honest nodes — detectable because chain halts); formal proof for threshold BLS in this model "still being worked on"; DKG key distribution can be biased "but doesn't matter for threshold signatures" — [drand security model](https://docs.drand.love/docs/security-model/)
- Filecoin spec restates the model: "drand assumes at least t of n nodes are honest and online. If that breaks, an adversary can halt randomness production but cannot bias it" — [Filecoin spec: drand](https://spec.filecoin.io/libraries/drand/)

**Consumers in production**
- Filecoin uses drand as "unbiasable entropy for leader election in Secret Leader Election (Expected Consensus)"; nodes fetch from relays (HTTP/S3/gossip), verify the BLS signature against the beacon public key and check Randomness = SHA256(Signature); epoch→round mapping formula from genesis times and periods; **"A drand outage halts Filecoin block production"**; after downtime drand catches up to wall-clock rounds and miners backdate blocks — [Filecoin spec: drand](https://spec.filecoin.io/libraries/drand/); [Filecoin docs: drand](https://docs.filecoin.io/basics/the-blockchain/drand)
- Filecoin switched from the 30 s chained mainnet beacon to quicknet under **FIP-0063 "Switching to new Drand mainnet network"**, codenamed Phoenix, "exactly 120 epochs (1 hour) after the Dragon upgrade" (nv22, epoch 3817920, 2024-04-11 14:00 UTC) — [Lotus v1.26.0 release notes](https://github.com/filecoin-project/lotus/releases/tag/v1.26.0); the chained/unchained verification path was decoupled from network version for devnet testing — [Lotus PR #11632](https://github.com/filecoin-project/lotus/pull/11632)
- Other stated uses: leader election, smart-contract randomness, COVID-19 random sampling, timelock decryption-key oracle, "an RNG certified by Gaming Labs International for several lottery games", sortition — [drand.love/about](https://www.drand.love/about)

**On-chain verification cost**
- Post-Pectra (EIP-2537) Solidity verification of a quicknet beacon (measured with `forge snapshot`, Aug 26 2025): BLS12-381 uncompressed sig 130,028 gas verify + 1,536 calldata = **131,564**; BLS12-381 compressed (48 B straight from the drand API) 139,812 + 768 = **140,580**; BN254 legacy 158,250 + 1,024 = **159,274**. Verified quicknet round 20986100 in mainnet block 23188016. Contract "not audited," "not meant for production." evmnet (BN254) "launched in 2024" for chains without BLS12-381 precompiles — [drand blog: verifying quicknet on Ethereum](https://docs.drand.love/blog/2025/08/26/verifying-bls12-on-ethereum)
- evmnet BN254 scheme: `expand_message_xmd` with keccak256 instead of sha256 (keccak "half as expensive in gas"; sha256 unavailable on some early zkEVMs); constant-time Fouque–Tibouchi SW map; verifier lib `kevincharm/bls-bn254`; RNGesus Reloaded gives drand a request/response model where "anyone can run a fulfiller without extra trust assumptions"; the original RNGesus (SNARK verifier for BLS12-381 beacons, ETHDenver 2023) was "impractical" and "still much costlier in gas overall" than BN254 verification — [kevincharm hackmd](https://hackmd.io/@kevincharm/rJA4r_Iia)

**Incidents**
- Status page (snapshot 2026-10-16): one listed incident — Apr 22 2026 14:43 UTC "Increased error rate on relays" affecting `/latest` and v2 APIs on mainnet and testnet relays; direct round queries unaffected; monitoring update 15:04 UTC (~21 min); all components "Operational"; no incidents Oct 2–16 2026; uptime percentages not shown — [status.drand.love](https://status.drand.love/)
- Spec-level statement of the real risk: "Any Drand beacon outage will effectively halt Filecoin block production" — [Filecoin docs: drand](https://docs.filecoin.io/basics/the-blockchain/drand)

### Inferences
- **Trust-model classification: external operator / fixed permissioned committee.** Operators are a closed consortium; membership changes via resharing ceremonies. A PoW L1 consuming drand would import (a) availability dependence on LoE, (b) unpredictability dependence on <12 of 22 colluding, and (c) release-timing leverage for an adversary holding the final share. It would *not* import bias risk (uniqueness).
- The 3 s quicknet period and unchained message H(r) means a PoW chain can commit to "round R" far in advance and later verify a 48-byte signature with one public key; the verification is a single 2-pairing equation e(σ, g2)·e(−H(m), pk) = 1 plus a hash-to-G1 (RFC 9380).
- The gas data imply BLS12-381 verification is roughly 1.1–1.2× cheaper than BN254 verification where native precompiles exist, but the dominant cost driver on a script chain without pairing opcodes is the pairing itself (see Q11).
- The ~21-minute relay incident in Apr 2026 affected the HTTP distribution layer, not beacon production; no production-halting incident was found on the status page, but the page only shows recent history.

### Gaps
- Current (2026) node count and threshold for quicknet: only the Oct 2023 figures (22–23 nodes, 12-of-22) were found; the LoE page gives no threshold. The default-chain deprecation status as of 2026 was not confirmed.
- Historical incident list before Oct 2026 (status page only shows recent window); no primary source found for any past beacon-halting outage.
- Hash-to-curve DST string for quicknet is not stated in the pages fetched (scheme ID `bls-unchained-g1-rfc9380` implies the RFC 9380 BLS ciphersuite, but the exact DST was not confirmed).

## Q2. Dfinity / Internet Computer random beacon

### Takeaway
ICP's beacon is a chained threshold-BLS signature per consensus round: nodes sign (round ‖ previous beacon), output = hash of the group signature; "low threshold" = strictly more than f shares (5 of 13 at n=13, f=floor((n−1)/3)), keys from a non-interactive DKG with resharing on membership change. Unbiasable by uniqueness; unpredictable while ≤ f nodes are corrupt; canisters get it one round later via `raw_rand`. Subnet membership is permissioned (node providers in a fixed subnet).

### Cited Findings
- Original design (DFINITY consensus paper, Rev.1, 2018-01-23): beacon is a VRF-like deterministic sequence ξ_r; each round, group members sign r ‖ ξ_{r−1}; output = hash of recovered group signature; bootstrap ξ_0 = nothing-up-my-sleeve (e.g., hash of "Dfinity"); t ∈ [f+1, n−f]; adversary cannot predict if f ≤ t−1 and cannot prevent creation if f ≤ n−t; uniqueness: "regardless of who signs, the resulting group signature will always be the same"; groups planned "in the order of 400" (this committee-of-400 design is superseded by today's subnet model) — [DFINITY consensus paper (2018)](https://dfinity.org/pdf-viewer/library/dfinity-consensus.pdf?theme=2019)
- PODC 2022 presentation: "At every height, there is an unpredictable random value shared by the nodes"; threshold BLS; "no last-actor bias"; non-interactive share creation; each node signs the previous beacon; example n=4, f=1 uses 2 shares; general rule f+1 of n=3f+1; NI-DKG with no trusted dealer — [IC Consensus PODC 2022 slides](https://DFINITY.ORG/presentations/ICConsensusPODC2022.pdf)
- Exact thresholds (Dfinity engineer Manu, 2024-04-15): f = floor((n−1)/3); **high threshold (certification, CUPs, notarization, finalization) = n−f = 9 of 13; low threshold (random beacon, random tape) = strictly more than f = 5 of 13** — [Dfinity forum: thresholds](https://forum.dfinity.org/t/what-are-the-thresholds-for-various-threshold-signatures/29579/3)
- NI-DKG: Groth, "Non-interactive distributed key generation and key resharing" (ePrint 2021/339, 2021-03-17); deployed on the IC for threshold BLS; pairing-based CCA-secure forward-secure encryption; chunked encryption; multi-receiver variant cuts ciphertext size up to 5×; proactive security via resharing when key-holder set changes — [ePrint 2021/339](https://eprint.iacr.org/2021/339)
- DKG "works over an asynchronous network" and "succeeds even if up to a third of a subnet's nodes are crashed or corrupt"; it can reshare an existing key when subnet membership changes; canister randomness: a signature on a special message is generated, hashed to a seed, numbers derived from the seed; "neither the seed nor the numbers can be predicted or biased, given the signature scheme's security" — [learn.internetcomputer.org: Subnet keys](https://learn.internetcomputer.org/hc/en-us/articles/34209540682644-Subnet-Keys-and-Subnet-Signatures)
- Developer docs: "VRF is seeded with the current round number", evaluated by subnet nodes with chain-key cryptography at "the same threshold used in the consensus protocol"; the output seeds a per-round PRNG (random tape) serving canisters that requested randomness the previous round; `raw_rand` returns 32 bytes from the random tape of the *next* execution round (one-round delay); only in update calls; **explicit caveat: "the subnet's VRF doesn't stop a canister from seeing the randomness and reacting before revealing the outcome" → commit-reveal recommended for fairness-critical apps** — [ICP docs: verifiable randomness](https://docs.internetcomputer.org/concepts/verifiable-randomness/)
- Chain-key page (updated 2026-04-25): scheme is "a derivative of BLS", modified for asynchronous consensus, dynamic subnet membership and resharing; each subnet has a stable public key, private key never reconstructed; typically tolerates up to a third Byzantine — [internetcomputer.org wiki: chain-key](https://internetcomputer.org/wiki/chain-key-cryptography/)
- Architecture doc: one beacon per round, "Only one valid beacon per height"; one random tape per round; generic shares "typically 2f+1 of 3f+1" (this generic figure conflicts with the forum's >f for the beacon specifically; the forum answer by a Dfinity engineer is more specific and should be preferred) — [mintlify.wiki dfinity/ic consensus](https://mintlify.wiki/dfinity/ic/architecture/consensus)

### Inferences
- **Trust-model classification: permissioned validator set (fixed subnet committee of node providers; membership and resharing governed by the network's governance system).** The low threshold (>f) is deliberately small: it maximizes availability (any f+1 honest nodes suffice) at the cost of requiring ≥ 2f+1 honest for unpredictability — i.e., unpredictability and the one-third fault bound coincide.
- Chaining (signing the previous beacon) makes the message unpredictable even to the signers until the previous round completes; combined with uniqueness, the only remaining adversarial power is withholding shares (availability), which the >f threshold neutralizes under the one-third assumption.
- A script-based PoW chain could verify an ICP beacon only if it could verify a BLS12-381 signature against a subnet public key; the same pairing-cost question as drand applies (Q11). No source showed anyone doing this.

### Gaps
- No primary source fetched states the precise message currently signed for the beacon (previous beacon ‖ height) in the production IC codebase; the 2018 paper and PODC slides describe chaining but not the exact encoding.
- No incident history for the IC random beacon was found.
- Production subnet sizes (13-node app subnets vs larger NNS subnet) only appear as the n=13 example in the forum answer.

## Q3. Aptos on-chain randomness (AIP-41 API, AIP-79 cryptography; weighted PVSS + VUF)

### Takeaway
Aptos validators run a weighted, non-interactive PVSS-based DKG every epoch (~2 h) and then produce a weighted VUF (BLS-style, unique) evaluation per block over (epoch, round); secrecy threshold 50% of stake, reconstruction threshold 66%, so under the <1/3 Byzantine PoS assumption the output is unpredictable until the block is ordered and unbiasable. The API blocks test-and-abort by compiler/VM rules (`#[randomness]` private entry functions only) but **does not currently prevent undergasing attacks** — that remains developer responsibility as of the docs' Sep 2026 update. Live on mainnet since the v1.12 node release (2024).

### Cited Findings
- Paper: "Distributed Randomness using Weighted VUFs" — Das (UIUC), Pinkas (Aptos Labs/Bar-Ilan), Tomescu, Xiang (Aptos Labs); received 2024-02-09, revised 2024-10-06. Weighted VUF whose per-party cost is independent of weight; new weighted PVSS with aggregatable transcript → DKG; evaluated on Aptos with **112 validators, total weight up to 4053; on-chain randomness adds only 133 ms latency** vs no randomness — [ePrint 2024/198](https://eprint.iacr.org/2024/198)
- From the PDF: threshold VUF defined with correctness, **uniqueness (unconditional, holds against unbounded adversaries)**, unforgeability (BDH assumption, ROM); static adversary may corrupt weight up to w (typically W/3); VUF evaluation requires combined weight > w; PVSS secrecy threshold t, reconstruction t+1; honest share count in the consensus setting is 2W/3; optimized weighted transcript has 3W group elements (naive 5W); each VUF share is a single group element independent of weight; VUF share verification 2 pairings per share; aggregator O(|T|) pairings; batched PVSS verification figures given inconsistently (4 vs 3 pairings) — [ePrint 2024/198 PDF](https://eprint.iacr.org/2024/198.pdf)
- AIP-79 (authors Tomescu, Xiang, Ma; created 2024-02-12; status Draft; target release v1.12): each epoch ends after 2 h or governance reconfiguration; each validator publishes a wPVSS transcript; validators aggregate once transcripts from 66% of stake are received; first finalized aggregated transcript completes the DKG; non-interactive, blockchain is the broadcast channel. **Secrecy threshold 50% of stake; reconstruction threshold 66% of stake** (ramp scheme from stake rounding; any subset meeting the reconstruction weight has stake ratio in (50%, 66%]). Per finalized block each validator computes a VUF share over (epoch, round) and reliably multicasts; shares beyond the reconstruction weight combine into the block seed, posted in a `BlockMetadataExt` transaction before all user txns; user txns derive a per-txn seed from block seed + txn metadata. Latency overhead "tens of milliseconds" on previewnet. Validator-set changes locked during DKG (~30 s every 2 h). Transcript size monitored against 1 MB state-item / 2 MB validator-txn-per-block limits. Risks: >50% colluding stake could leak the VUF key and predict an epoch's randomness (MEV); DKG failure stalls epoch change (mitigation: force epoch change, disable randomness); randomness-generation failure halts chain (mitigation: disable via local config). "Randomness calls must come from private entry functions, to block test-and-abort attacks." — [AIP-79](https://github.com/aptos-foundation/AIPs/blob/main/aips/aip-79.md)
- aptos-node v1.12.0 release (dated "10 May", year not shown on page; AIP-79 created Feb 2024 and targets v1.12 → 2024) lists "[AIP-79] Implementation of instant on-chain randomness," adds `randomness_config` and `randomness_api_v0_config` on-chain configs — [aptos-node-v1.12.0 release](https://github.com/aptos-labs/aptos-core/releases/tag/aptos-node-v1.12.0)
- Forum "Randomness enabled now on Aptos": states the instant on-chain randomness API is live on mainnet (no date on page) — [Aptos forum](https://forum.aptosfoundation.org/t/randomness-enabled-now-on-aptos/10757)
- Forum "Roll with Move" (Tomescu & Xiang): components wPVSS, wDKG, wVRF; "secure as long as adversaries control less than 50% of stake"; criticizes DFINITY's approach as "less secure for PoS", external beacons (drand) as requiring external trust + commit-reveal, VDFs as not instant, and **claims Flow and Celo designs are "susceptible to bias and predictability by malicious validators" (no mechanism given)** — [Aptos forum: Roll with Move](https://forum.aptosfoundation.org/t/roll-with-move-secure-instant-randomness-on-aptos-by-alin-tomescu-and-zhuolun-xiang/10047)
- Developer docs (last updated 2026-09-14): `0x1::randomness` with `u8…u256_integer()`, `*_range()`, `bytes(n)`, `permutation(n)`; must be called from a **private entry function annotated `#[randomness]`**; VM checks the outermost call is such a function, else whole txn aborts; Move scripts unsupported; randomness-dependent `public` functions are a compile error (`#[lint::allow_unsafe_randomness]` bypasses). **Test-and-abort**: attacker contract calls a public randomness helper, reads the result, aborts on bad outcomes, repeats — blocked by the compiler check. **Undergasing**: attacker sets `max_gas` so expensive branches run out of gas; example toss 9 gas, reward 10, cleanup 100, `max_gas=108` → cleanup always fails → retry until reward; **"The randomness API currently does not prevent undergasing attacks"** — mitigations are developer-side (outcome-independent gas, admin-only callers, make the most beneficial path the most expensive — "tricky, gas schedules can change"); seed is public so never use for secrets — [Aptos docs: Randomness API](https://aptos.dev/build/smart-contracts/randomness)

### Inferences
- **Trust-model classification: permissioned-by-stake validator set (PoS, ~100+ validators), fixed per epoch via DKG.** The design is fully validator-native (no external operator), but it presupposes a BFT validator set with known stakes — unavailable on a PoW chain.
- The 50%/66% ramp means the practical guarantee is: unpredictable while < 50% stake colludes; live while ≥ 66% stake is honest and online; consistent with the standard <1/3 Byzantine assumption with slack for weight rounding.
- The undergasing attack is a general property of any "instant" randomness exposed inside a transaction whose caller controls the gas budget; it is orthogonal to the beacon's cryptography and would afflict any UTXO/script design exposing randomness to scripts with caller-controlled fee limits. (Sui's docs describe the same class of attack under "resource limits"; see Q4.)

### Gaps
- AIP-41 text could not be fetched (GitHub returned client error / robots block); the undergasing "fix" discussed in AIP-41 (e.g., a required gas deposit) is therefore unconfirmed. The Sep 2026 docs state the API still does not prevent undergasing, which suggests no protocol-level fix has shipped, but this is inference from absence.
- Exact mainnet enablement date (governance proposal date) not found; only "live" and the v1.12 release.
- Current validator count and DKG transcript sizes on mainnet in 2026 not found.

## Q4. Sui native randomness (DKG + threshold BLS, 2024)

### Takeaway
Sui runs a DKG (fastcrypto `dkg_v1`, BLS12-381) among the validator committee at each epoch start, with stake weights reduced to small integers and threshold t set at the f+1 validity threshold (3,334 of 10,000 voting power); partial signatures over a round number are combined in parallel with consensus so randomness is available after ordering, before execution. Guarantees: unpredictable and unbiasable "as long as less than one-third of voting power is corrupted." Testnet Jun 2024, mainnet Aug 21 2024 (v1.31). Test-and-abort is blocked by Move/PTB rules; resource-limit (gas) attacks are not automatically prevented. A DKG-failure state bug contributed to a ~6 h mainnet outage on May 29, 2026.

### Cited Findings
- Announcement (2024-06-13): "At the start of each epoch, validators run a DKG protocol to create secret shares of a distributed key. During the epoch, they use those shares to produce randomness"; generation "runs in parallel with consensus," values available "after a transaction is ordered but before it executes"; **unpredictability** (nobody knows values before use — prevents front-running/selective engagement) and **unbiasability** (no single party can influence outcome); "security holds as long as less than one-third of the network's voting power is corrupted"; keys re-established every epoch; Move access via `sui::random` with a `&Random` object and `new_generator(rnd, ctx)`; contrasted with drand (must wait for a future round) and VDFs (too slow); available on Testnet, mainnet "not yet" — [sui.io blog: secure native randomness](https://www.sui.io/blog/secure-native-randomness-testnet)
- Mainnet: "the Random Beacon, which provides Sui's onchain randomness, will go live on mainnet on **August 21, 2024**, with the Sui **v1.31** release" (newsletter dated 2024-08-15) — [Sui Dev Newsletter ed. 9](https://buttondown.com/suidevnewsletter/archive/edition-9/)
- Source (`sui-core/src/epoch/randomness.rs`): DKG library `fastcrypto_tbls` (`dkg_v1`, `nodes`, `ecies_v1`), random oracle seeded with chain id + epoch; keys are `bls12381::G2Element`; validator BLS authority key converted to the DKG private scalar; **threshold t derived from `committee.validity_threshold()` via `Nodes::new_reduced(...)`**; node weight = stake as `u16`, reduced per protocol config (`random_beacon_reduction_allowed_delta`, `random_beacon_reduction_lower_bound`); rounds (`RandomnessRound`) reserved only after `random_beacon_min_round_interval_ms`; `send_partial_signatures(epoch, round)`; a round is reserved as part of a consensus commit batch; **"If DKG times out … randomness is disabled for the epoch and randomness-using transactions fail"** — [randomness.rs](https://github.com/MystenLabs/sui/blob/main/crates/sui-core/src/epoch/randomness.rs)
- Committee constants: `TOTAL_VOTING_POWER = 10_000`; `QUORUM_THRESHOLD = 6_667`; **`VALIDITY_THRESHOLD = 3_334` ("defined by f+1")** — [committee.rs](https://github.com/MystenLabs/sui/blob/main/crates/sui-types/src/committee.rs)
- Developer docs: `Random` is a shared object at `0x8`, immutable; `RandomGenerator` via `new_generator`; **restrictions**: functions taking `&Random` must be private `entry` (compiler rejects `public`); **Sui rejects a PTB if any command after a `MoveCall` using `Random` is anything other than `TransferObjects` or `MergeCoins`** (blocks appending a revert check); `RandomGenerator` cannot be a public-function parameter (caller could serialize and predict). **Test-and-abort** described (PTB can run game then revert, cancelling fee payment, retry with fresh randomness); mitigation "divide logic" across two transactions (commit value to an object unreadable in that txn; charge fee up front). **Resource limits/gas: "An attacker may try to force a transaction to run out of resources at a chosen point. The `Random` API does not prevent this automatically"**; mitigations: balanced gas paths, heavy work on the main path, profile costs — [Sui docs: onchain randomness](https://docs.sui.io/guides/developer/advanced/randomness-onchain)

(Inference from `validity_threshold` → `t`; the exact mapping inside `fastcrypto_tbls` was not read.)
- The May 2026 incident shows the operational coupling risk of validator-native DKG beacons: a DKG liveness edge case can stall the whole chain's epoch transition, not just randomness.

## Q5. Flow Random Beacon and "secure randomness for smart contracts"

### Takeaway
Flow's beacon is a Dfinity-style threshold BLS (BLS12-381, sigs in G1) run by a "random beacon committee" of consensus nodes whose shares ride inside HotStuff votes; keys come from a Joint-Feldman (Pedersen) DKG run each ~1-week epoch via the `FlowDKG` contract, threshold t = floor((n−1)/2) (reconstruction needs t+1). ### Cited Findings

## Q6. Algorand VRF seed and cryptographic sortition

### Takeaway
Algorand's seed evolves as Q^r = H(VRF_leader(Q^{r−δs}), r) with a seed lookback δs = 2 rounds and periodic re-randomization with a block digest from δs·δr = 160 rounds back; the proposer's only bias lever is to withhold (forcing the H(Q^{r−1}, r) branch) or, with multiple credentials, choose which to broadcast — giving "at most two possible values" per round. Formal analyses show the gain is small (a 10% staker leads at most ~10.15% of rounds; a well-connected 20% staker at least 20.68%). No threshold cryptography; permissionless-by-stake but inherently biasable by a bounded amount.

### Cited Findings
- Chen & Micali: if block r is non-empty, **Q^r = H(SIG_{ℓ^r}(Q^{r−1}), r)** (leader's signature = VRF output); if empty, **Q^r = H(Q^{r−1}, r)** — "absolutely mandatory" because a leader can withhold its credential or force an empty block; a malicious leader "can produce at most two possible values for Q^r"; leader selection H(SIG_i(r,1,Q^{r−1})) ≤ p; look-back k: selection pool fixed k rounds in advance so late joiners can't influence the seed; honest leader probability h' > h²(1+h−h²) → > 0.7424 at h = 80%; honest-majority-of-money h > 1/2, BA committees need > 2/3 honest — [Algorand paper arXiv:1607.01341](https://arxiv.org/pdf/1607.01341)
- Spec (non-normative): period p=0: proposer computes VRF y over seed from round r−δs, α = H(I ‖ ProofToHash(y)); period p>0 (re-proposal): y=0, α = H(seed_{r−δs}) — proposer input excluded "to avoid the possibility of seed manipulation by malicious proposers"; re-randomization when r mod (δs·δr) < δs: Q = H(α ‖ H(L[r−δs·δr])) mixing in the block digest 160 rounds back; example values **δs = 2, δr = 80** — [Algorand spec: seed calculation](https://specs.algorand.co/abft/non-normative/abft-nn-seed-calculation)
- go-algorand `config/consensus.go`: `SeedLookback = 2` ("how many blocks back we use seeds from in sortition. delta_s in the spec"); `SeedRefreshInterval = 80` in v8 (100 in v7; "how often an old block hash is mixed into the seed. delta_r"); `MaxBalLookback = 320` ("oldest round the ledger must answer balance queries for"); v8 comment: "uses parameters and a seed derivation policy (the 'twin seeds') from Georgios' new analysis" — [go-algorand consensus.go](https://github.com/algorand/go-algorand/blob/master/config/consensus.go)
- Optimal manipulation (Ferreira, Ganesh, Huh, Weinberg, Yu, Hourigan; EC'24, arXiv 2024-06-21): strategic staker with stake α chooses which credential to broadcast or stays silent; β = network connectivity (β=1 sees honest credentials first); **10% staker, β=1: leads at most 10.15% of rounds (bounds [10.08%, 10.15%]); β=0, 10%: ≤ 10.09%; β=0, 20%: ≤ 20.21%; β=1, 20%: ≥ 20.68% (~320% amplification of marginal gain)**; κ ≈ 0.38 is the omniscient-adversary threshold above which reward → 1 — [arXiv:2406.15282](https://arxiv.org/pdf/2406.15282)
- Developer docs: the block seed "is generated per block and used in consensus sortition"; "Participation nodes can influence it, for example by withholding a block. So … the block seed should not be used directly as a randomness source"; smart-contract randomness instead comes from an off-chain **VRF oracle/beacon** (AVM 7 `vrf_verify` + `block` opcodes) that signs the block seed every ~8 rounds; the example design has a single operator; dApps must commit to a future round before it occurs — [Algorand dev docs: Randomness](https://developer.algorand.org/articles/randomness-on-algorand)

### Inferences
- **Trust-model classification: permissionless-by-stake validator-native (no committee, no DKG) — but biasable.** Each round's proposer has ≤ 1 bit (two options) of influence; the "lookback" (δs = 2 for the seed; 320 rounds for balances) limits what the adversary can plan but does not remove the bit.
- Algorand's own developer guidance that the consensus seed "should not be used directly" and that app randomness comes from an operator-run VRF oracle is the clearest primary-source admission that a VRF-chain seed is not application-grade unbiasable randomness.

### Gaps
- The v8 "twin seeds" analysis ("Georgios' new analysis") was not located as a public document.
- No source quantified the bias of the *seed* (as opposed to leader-election share) in bits per round beyond "at most two possible values."

## Q7. Cardano Ouroboros Praos epoch nonce and grinding

### Takeaway
The Praos epoch nonce is a BLAKE2b-256 fold of block VRF outputs over the first part of the previous epoch; an adversary controlling trailing slots of the nonce window can choose among 2^t nonces by publishing/withholding (self-mixing) or 2^(|A|−|H|) via private forking. IOG's CPS-0021/CPD (2025–26) estimates attacks become "significantly more feasible" above ~20% stake (≈4.36 B ADA, Mar 2025), with grinding cost from ~$56 (ρ=20) to ~$3.1 B (ρ=50); Gaži–Quader–Russell (ASIACRYPT 2025) prove the beacon secure against ≤ ~12% stake without bounding grinding computation. Proposed fix CIP-0161 "Phalanx" adds a Wesolowski class-group VDF (12 CPU-hours per epoch) — i.e., Cardano's own path to unbiasability is a VDF.

### Cited Findings
- Nonce construction: evolving nonce η_{t+1} = η_t ⭒ VRF_{t+1} (concatenate then BLAKE2b-256), initialized from `extraEntropy`; candidate nonce for epoch e = evolving nonce at end of Phase 2 of epoch e−1; epoch nonce η_e combines candidate with evolving nonce at end of e−2. Phases per epoch (10k/f slots): Phase 1 stake stabilization 3k/f; Phase 2 "honest randomness" ≥ 1k/f (analysis uses 6k/f); Phase 3 nonce stabilization 4k/f; with f = 1/20, k = 2,160: epoch = 432,000 slots (5 days), S2 = 259,200 slots — [CPS-0021 annex (CPD)](https://cips.cardano.org/cps/cps-0021/annex/CPD)
- Grinding mechanics: adversary with t trailing blocks at the end of Phase 2 picks among **2^t nonces** by proposing/missing each (self-mixing); forking (preemptive ex-ante or reactive ex-post reorg) gives **2^x choices with x = |A| − |H|** in the interval; grinding depth ρ = log₂(choices), 0 ≤ ρ ≤ 256. Self-mixing E(X_A): 0.005 @0.5% stake, 0.111 @10%, 0.250 @20%, 0.667 @40%, 0.961 @49% — called "neither highly probable nor particularly critical"; expected grinding power "rises sharply above roughly 20% stake"; at 5% stake ~1,800 years on average for a 4-block advantage. Cost model T_grinding = T_nonce + T_distribution + T_eval (VRF outputs precomputable). **Cost: ρ = 20 ≈ $56; ρ = 50 ≈ $3.1 billion**; feasibility bands e.g. "Ant Glance" trivial for ρ 0–53.6, infeasible above ~79.4; "Owl Survey" trivial 0–31.1, infeasible above ~57.7; 10-year (3,650-epoch) horizon; 20% stake ≈ 4.36 B ADA (2025-03-01) — [CPS-0021 annex (CPD)](https://cips.cardano.org/cps/cps-0021/annex/CPD)
- CPS-0021 "Ouroboros Randomness Manipulation" (Henin, Toledo; created 2025-10-03, updated 2026-06-09; status Open): grinding lets an adversary cluster slot leadership, amplifying private forking, selfish mining, double-spend and censorship; proposed solutions CIP-0140 (Peras) and CIP-0161 (Phalanx); full elimination research cites ePrint 2021/1698 "Efficient Random Beacons with Adaptive Security for Ungrindable Blockchains" — [CPS-0021](https://cips.cardano.org/cps/CPS-0021)
- **CIP-0161 Ouroboros Phalanx** (Proposed; created 2025-07-25, updated 2026-06-23; requires hard fork): adds a **Wesolowski VDF over class groups** (4,096-bit discriminant, 2,048-bit group) to nonce generation; epoch split into 120 one-hour intervals (3,600 slots; 82 computation + 36 catch-up); compute budget T_Φ = 12 CPU-hours per epoch (~527 s per node); grinding resistance ρ = 64; λ = 128; honest stake σ = 0.51 (secure up to 49% adversarial); claims grinding cost rises ~10^10×; ASIC speedup assumed ≤ ~10× (Chia's ASICs 3–5× faster than CPU); "best-effort design," no formal non-amortizability guarantee — [CIP-0161](https://cips.cardano.org/cip/CIP-0161)
- "Taming Iterative Grinding Attacks on Blockchain Beacons" (Gaži [IOG], Quader [Google], Russell [UConn/IOG]; ASIACRYPT 2025; ePrint 2025/1974, 2025-10-22): defines "natural grinding capacity"; tail bounds give smooth min-entropy guarantees regardless of beacon internals; applied to Praos, **the beacon is secure against adversaries controlling up to ~12% of stake "without assuming a bound on the computation spent on grinding"** — a new guarantee for the protocol — [ePrint 2025/1974](https://eprint.iacr.org/2025/1974)

### Inferences
- **Trust-model classification: permissionless-by-stake validator-native (no committee/DKG), biasable.** The documented bias is exponential in the adversary's trailing-slot count; Cardano's remediation (Phalanx) is a VDF, confirming that stake-weighted VRF chains cannot reach unbiasability without a delay function or a threshold committee.
- The ~12% (provable, computation-unbounded) vs ~20% (IOG's practical feasibility knee) figures bracket the real-world safety margin of a Praos-style nonce.

### Gaps
- The CPD's explicit hash-evaluation counts behind the $56/$3.1 B figures were not extracted (only the ρ values).

## Q8. Ethereum RANDAO

### Takeaway
RANDAO mixes, per block, hash(proposer's BLS signature over the epoch) by XOR; the mix at the end of epoch N fixes duties for epoch N+2 (MIN_SEED_LOOKAHEAD = 1). A proposer controlling the last k consecutive slots of an epoch picks among 2^k outcomes by revealing or skipping (cost: lost CL+EL rewards per skipped slot). Theory (2023) and later work (2025) show large pools (25–33%) can meaningfully steer future proposer slots (e.g., 33% → 99.5% success at securing a target slot; 28% → 65%); empirical mainnet measurements through Jan 2025 found "no statistically significant traces." Lotteries/casinos reading RANDAO are explicitly flagged as vulnerable; no documented dApp loss was found.

### Cited Findings
- Spec constants: `BLSSignature` = Bytes96 (BLS12-381 signature, 96 bytes); `SLOTS_PER_EPOCH` = 32; `get_seed(state, epoch, domain)` = hash(domain ‖ epoch ‖ mix) with mix = `get_randao_mix(state, epoch + EPOCHS_PER_HISTORICAL_VECTOR − MIN_SEED_LOOKAHEAD − 1)`; `randao_mixes` initialized with the eth1 block hash; timing table shows values 1 epoch (6.4 min) and 4 epochs (25.6 min) in the MIN/MAX_SEED_LOOKAHEAD positions (labels stripped in extraction; mapping inferred from row order) — [consensus-specs phase0](https://github.com/ethereum/consensus-specs/blob/dev/specs/phase0/beacon-chain.md)
- Mechanics and bias model (Nero_eth / Toni Wahrstätter, ethresear.ch, 2023-07-10): each proposer's BLS signature over the current epoch number is hashed and XORed into the mix; empty slots can't update it; duties for epoch N_t use the mix at the last slot of N_{t−2}; **only consecutive tail slots matter; each is a binary reveal/skip choice → 2^x outcomes (256 for 8 tail slots)**; skipping forfeits EL and CL rewards. Binomial model: 25% stake expects ~8 proposer slots/epoch; P(≥9 slots in N+2) ≈ 40%; with 2 tail slots P(≥10) ≈ 70%. Lido had 8 consecutive tail slots twice (epochs 149818, 184869) and 18,586 single-tail-slot instances since the Merge; at epoch 184869 the best strategy (miss 4 of 8) would have yielded 16 proposers in N+2 (12 after subtracting missed-slot cost) vs the actual 7; Coinbase (~7–8%) "could have had 7 more proposers" in the first week of July 2023 vs 3,528 expected; targeting: 25% stake with 2 tail slots can reach 23 distinct slots in N+2, 10% stake → 12. **"Smart-contract casinos or lotteries drawing winners from RANDAO are vulnerable"**; FOMO3D-style games exposed. Manipulation not reported as observed; mitigations discussed: social slashing, VDF (no implementation plans); mkalinin suggested a 16-epoch delay between bidding close and draw — [ethresear.ch: Selfish Mixing](https://ethresear.ch/t/selfish-mixing-and-randao-manipulation/16081)
- "Forking the RANDAO" (Nagy, Tapolcai, Ladóczki, Seres; ePrint 2025/037, 2025-01-09): new attack class — selectively forking out an honest proposer's block (using proposer boost) to manipulate the mix without losing own slots (lost slots are later compensated); forking + selfish mixing is the most powerful known strategy; **"measurements of Ethereum mainnet found no statistically significant traces of these attacks to date"** — [ePrint 2025/037](https://eprint.iacr.org/2025/037); companion post lists countermeasures: longer epochs, lower proposer boost, single-slot finality; long-term: VDFs (dishonest majority) or weighted threshold VRFs (honest majority); open questions include a RANDAO bribery market and MEV-aware models — [ethresear.ch: Forking the RANDAO](https://ethresear.ch/t/forking-the-randao-manipulating-ethereums-distributed-randomness-beacon/21414)
- "Slot à la carte" (Tapolcai, Ladóczki, Nagy; ePrint 2025/219, 2025-02-13): colluding **33% of validators can secure a foreseen lucrative slot with 99.5% success**; RANDAO "seriously vulnerable to manipulations in its current form" — [ePrint 2025/219](https://eprint.iacr.org/2025/219); forum summary (2025-02-13): largest pool α = 28% → 65% chance of controlling any given slot; at 28% the adversary averages **24 RANDAO outcomes to choose from (~5 bits)**; average cost 1.1 sacrificed own slots + ~0.5 honest slots forked out; detection hard because missed slots look like network issues — [ethresear.ch: RANDAO target slot attack](https://ethresear.ch/t/randao-target-slot-attack-analysis/21740)

### Inferences
- **Trust-model classification: permissionless-by-stake validator-native (no committee), biasable; bias ≈ 1 bit per controlled tail slot, amplified by forking.** The MEV connection is explicit in the sources: skipping is rational "in high-MEV periods," and the forking variant avoids the skip cost entirely.
- The absence of statistically detectable manipulation on mainnet (as of Jan 2025) is evidence of behavior, not of security; both 2025 papers argue the attack is profitable for the largest pools.
- For a lottery, the relevant model is the adversary's number of selectable outcomes (2^k, or ~24 for a 28% pool), not "one bit": a prize larger than ~k × (block reward + MEV) makes manipulation rational.

- `process_randao` body could not be extracted from the spec page (truncated); the XOR/hash mechanics are cited from the ethresear.ch post instead. eth2book chapter was unreachable (server error).
- No documented case of a dApp/lottery loss caused by RANDAO bias was found; only vulnerability warnings.
- No empirical study after Jan 2025 was found within the search budget.

## Q10. Commit–reveal with deposits (RANDAO-contract style) — why unsuitable for high-value draws

### Takeaway
Any commit-reveal beacon without a delay function faces Cleve's 1986 bound (bias ≥ ε/(4r+1), i.e., Ω(1/r)) when fewer than a majority are honest; Bonneau–Bünz–Christ–Efron (2024) prove that circumventing it *requires* a delay function, and classify commit-reveal-punish (deposit) schemes as still needing an honest majority — penalties bound the attacker's cost, not the attack. The last revealer can always abort after seeing everyone else's value, so a deposit only works if it exceeds the value of choosing between the two outcomes.

### Cited Findings
- "Good things come to those who wait: Dishonest-Majority Coin-Flipping Requires Delay Functions" (Bonneau [NYU/a16z], Bünz [NYU], Christ, Efron [Columbia]; ePrint 2024/1711): Cleve's theorem — an ε-consistent r-round two-party protocol can be biased by ≥ ε/(4r+1) (≈ Ω(1/r)); **any protocol circumventing Cleve's bound implies a (weak) delay function (Thm 3, 5), and weak delay functions suffice for an n-party DRB secure against n−1 sequentially-bounded corruptions in the ROM (Thm 7, Cor 2)**; commit-reveal is "vulnerable to a last-revealer attack: a malicious participant can drop out after seeing others' reveals"; commit-reveal-punish protocols "rely on an honest majority or supermajority"; Ethereum-style penalized systems "still require an honest majority to obtain any security guarantees" — [ePrint 2024/1711](https://eprint.iacr.org/2024/1711.pdf)
- Commit-Reveal² (Lee, Gee, Soroush, Bingol, Huang; arXiv 2504.03936, Apr 2025; IEEE ICBC 2025): simple commit-reveal beacons "are vulnerable to last-revealer strategies" and existing descriptions "often leave accountability and recovery undefined"; proposes cryptographically randomizing the final reveal order, off-chain coordination with on-chain commitments/slashing/recovery; claims unpredictability and bit-wise bias resistance in the ROM; >80% gas reduction vs fully on-chain baseline for small/moderate operator sets — [arXiv:2504.03936](https://arxiv.org/abs/2504.03936v2)
- The same abort problem recurs at the application layer even on threshold beacons: Sui and Aptos both block "test-and-abort" by language/PTB rules (Q3, Q4); Flow's commit-reveal explicitly accepts that "the user can still abort the reveal after seeing a losing result, but the bid is lost when the window expires" — [Flow docs: Randomness](https://developers.flow.com/build/advanced-concepts/randomness); ICP recommends commit-reveal because a canister "can see the randomness and react before revealing" — [ICP docs](https://docs.internetcomputer.org/concepts/verifiable-randomness/)
- RANDAO's own tail-slot bias is the live example of commit-reveal-with-penalty: the "penalty" is the forfeited slot reward, and the forking variant removes even that cost (Q8) — [ethresear.ch: Selfish Mixing](https://ethresear.ch/t/selfish-mixing-and-randao-manipulation/16081); [ePrint 2025/037](https://eprint.iacr.org/2025/037)

### Inferences
- A deposit-based commit-reveal lottery is secure only when deposit > (prize × probability swing obtainable by aborting) for every participant and coalition, which is unbounded for a high-value draw; the formal results say no protocol structure (ordering, rounds, penalties) fixes this without either an honest majority of participants (→ threshold committee) or sequential delay (→ VDF).
- Commit-Reveal² lowers the *probability* that a specific adversary is last but does not change the Cleve bound; it is a mitigation, not a guarantee, and relies on an operator set with slashing.

### Gaps
- No formal bound specific to deposit-based schemes (e.g., optimal deposit as a function of prize) was found in the sources fetched; the 2024/1711 paper explicitly does not analyze penalty mechanisms formally.

## Q11. What a UTXO/script chain (Schnorr CHECKSIG, SHA256/BLAKE2b, OP_CAT, 64-bit arithmetic, Groth16 verifier opcode) could actually consume

### Takeaway
Without a pairing opcode, the only threshold beacon that is verifiable *directly* in script is none of them; the practical route is a Groth16 proof that "σ is a valid BLS signature on H(round) under pk" — which is well-trodden but heavy: ~19.2M R1CS constraints (circom-pairing `verify`, ~2 min proving on a 32-core box), ~2.1–2.7M R1CS for the pairing part in gnark's emulated BLS12-381-over-BN254 (ACNS 2023), 27M for Telepathy's full step circuit (118 s). RNGesus (ETHDenver 2023) did exactly "drand BLS12-381 inside a SNARK for EVM" as a proof-of-concept and its author later judged it impractical versus native BN254 verification. A drand/evmnet-style BN254 beacon does not help a chain with no pairing opcode. All VRF-seed chains (Algorand/Praos/RANDAO/BABE) are irrelevant as external beacons because they are biasable and their outputs are not independently verifiable without their full consensus state.

### Cited Findings
- circom-pairing (0xPARC / yi-sun) BLS12-381 benchmarks on AWS r5.8xlarge (32-core 3.1 GHz, 256 GB): **`verify` (BLS signature verification) 19.2M non-linear constraints, witness gen 2.6 min, rapidsnark proving 2 min, verification 1 s; `optimalate` (optimal Ate pairing) 11.4M constraints, 52 s proving; `maptoG2` (hash-to-curve) 2M constraints, 6 s; `subgroupcheckG1` 789K; `subgroupcheckG2` 819K** — [circom-pairing README](https://github.com/yi-sun/circom-pairing/blob/master/README.md)
- gnark emulated BLS12-381 pairing over BN254 (Groth16/R1CS; El Housni, ACNS 2023, ePrint 2022/1162): **1 pairing 2,088,277 constraints; 2 pairings 2,682,342; 4 pairings 3,895,167; Miller loop only 898,237; final exponentiation ~1.19–1.21M; 1 pairing with fixed G2 argument 1,868,541** — [yelhousni hackmd: emulated pairing](https://hackmd.io/@yelhousni/emulated-pairing); paper — [ePrint 2022/1162](https://eprint.iacr.org/2022/1162)
- Telepathy (Succinct) circom sync-committee circuits: step circuit (BLS12-381 aggregate verification incl. one pairing + 512 G1 adds) **27M constraints, 124 s witness, 118 s proving**; rotate circuit 68M constraints, 60 s proving; AWS r6a.8xlarge (32 cores, 256 GB) — [Telepathy docs: circuits](https://docs.telepathy.xyz/protocol/circuits)
- Sisu (arXiv 2404.10404) cites the circom-pairing BLS12-381 signature verification at **19.2M constraints**; witness generation for a 25M-constraint circuit ≈ 2.5 min with rapidsnark; MSM 2^24 ≈ 3.6 s on a GTX 1080 — [arXiv:2404.10404](https://arxiv.org/pdf/2404.10404)
- RNGesus (kevincharm, ETHDenver 2023): "anyone can submit a SNARK proof that the round's BLS signature is valid," circuits forked from circom-pairing; labeled "PROOF OF CONCEPT // UNOPTIMISED // UNAUDITED // DO NOT USE IN PROD"; moving hash_to_field out of Solidity "would save ~850k gas" — [kevincharm/rngesus](https://github.com/kevincharm/rngesus); the author's later writeup calls the SNARK approach "impractical" and "still much costlier in gas overall" than BN254 native verification, which motivated the BN254 evmnet — [kevincharm hackmd](https://hackmd.io/@kevincharm/rJA4r_Iia)
- quicknet verification equation and inputs that a circuit would have to reproduce: message = SHA-256(8-byte BE round) (round-only, unchained), hash-to-G1 per RFC 9380, check e(σ, g2) = e(H(m), pk) with σ ∈ G1 (48 B), pk ∈ G2 (96 B) — [verifier.rs](https://www.bittensor.com/code/raw/pallets/drand/src/verifier.rs); [drand blog: quicknet](https://docs.drand.love/blog/2023/10/16/quicknet-is-live)
- Native-precompile reference point for comparison: 130k–140k gas on Ethereum post-Pectra — [drand blog: verifying on Ethereum](https://docs.drand.love/blog/2025/08/26/verifying-bls12-on-ethereum)

### Inferences
- **Direct script verification is infeasible**: Schnorr CHECKSIG + SHA256/BLAKE2b + OP_CAT + 64-bit arithmetic cannot evaluate a BLS12-381 (or BN254) pairing; none of the threshold beacons (drand, ICP, Aptos, Sui, Flow) can be checked without pairings. Only beacons whose proof is a Schnorr/ECVRF-style signature on a curve the chain already has (e.g., a single-key VRF) would be script-verifiable — but a single-key VRF reintroduces an operator who can withhold.
- **Groth16 route**: a circuit proving "σ verifies under the fixed quicknet pk on message H(round)" needs (a) hash-to-G1 (SHA-256 expand_message_xmd + SSWU map; circom's G2 version is ~2M constraints, G1 should be smaller — not benchmarked in sources), (b) one 2-pairing product check (~2.7M R1CS in gnark emulation; 11.4M for circom's single optimal Ate), (c) subgroup check on σ (~0.8M). Order of magnitude: **~3–5M R1CS (gnark-style) to ~15–20M (circom-pairing-style)**, proving time seconds-to-minutes on a 32-core server, one on-chain Groth16 verification (fixed cost via the opcode). The fixed-G2 optimization (1.87M vs 2.09M per pairing) applies because pk and g2 are constants. These totals are my synthesis; no source gives an end-to-end "drand-in-Groth16" constraint count other than RNGesus (unstated).
- **Curve mismatch caveat**: if the chain's Groth16 opcode verifies proofs over BN254, BLS12-381 arithmetic is non-native (the gnark numbers above). If the opcode verifies Groth16 over BLS12-381, BLS12-381 pairing arithmetic is *still* non-native inside the circuit (the circuit's field is the scalar field Fr, the pairing is over Fq), so emulation costs remain; a 2-chain (e.g., BLS12-377 inner / BW6-761 outer) would make it native but requires a different beacon curve than drand uses.
- **What this buys and what it doesn't**: Groth16-wrapping drand gives a PoW chain an *unbiasable* external beacon (uniqueness) with *no bias path for miners* — but imports LoE as an **external operator** for availability and unpredictability (< 12-of-22 collusion), plus a trusted Groth16 setup for the circuit. It does not make the chain operatorless. Verifying the chain's own PoW-derived randomness remains biasable by miners (grinding), which is the problem drand would be imported to avoid.
- Sui/Aptos/Flow/ICP beacons are consumable the same way in principle (threshold BLS12-381 with an epoch public key) but their public keys rotate every epoch (Sui/Aptos ~2 h–1 day, Flow ~1 week), so a consumer would also need to verify key-rotation (DKG result) chains — far more state than drand's fixed key. drand's non-rotating group key (resharing keeps it unchanged) is what makes it the only practical external target.

### Gaps
- No public project was found that verifies a drand *quicknet* (G1-signature) beacon inside Groth16 with a published constraint count; RNGesus (2023) targeted the then-current chained/G2 beacons and reported no numbers.
- No benchmark for hash-to-G1 (SSWU on G1) constraint count was found; only `maptoG2` (2M, circom).
- No source addresses a Groth16 verifier *opcode* on a UTXO chain consuming an external beacon; the above is reasoned from component costs.

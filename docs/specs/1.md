# M1 spec — Shard, bundles and `buy()`

Status: approved 2026-10-10; implemented in M1 with the corrections marked "(corrected)" (see `docs/DECISIONS.md`). Design references are to `docs/design.md` v0.4.1.

M1 builds the shard covenant with `buy()`, the ticket's state layout, the counter tree and the off-chain builder for `buy()`. It also settles the five open decisions listed for M1 in `docs/milestones.md`. Nothing here touches `close()`, `draw()` or `claim()` logic.

## 1. Decisions settled in this spec

Each one becomes a row in `docs/DECISIONS.md` when M1 is recorded.

## 3. Counter tree

### 3.1 Combination and rank

A combination is 6 bytes: n1 n2 n3 n4 n5 bonus, each one byte. It is canonical when 1 ≤ n1 < n2 < n3 < n4 < n5 ≤ 30 and 1 ≤ bonus ≤ m. Only canonical combinations are accepted, so each holding has exactly one encoding.

The key is the colex rank of the main numbers:

> rank = C(n1 − 1, 1) + C(n2 − 1, 2) + C(n3 − 1, 3) + C(n4 − 1, 4) + C(n5 − 1, 5)

It is a bijection from canonical main-number sets onto 0..142,505 ((1,2,3,4,5) → 0; (26,27,28,29,30) → 142,505). The script computes the rank from the combination; no caller supplies a key.

### 3.2 Hashing (domain-separated, OpBlake2b)

- Non-empty leaf: `H(0x00 ‖ rank as 3-byte script number ‖ counts)`, where counts is 2m bytes: count for bonus 1, then bonus 2, …, each a 2-byte script number.
- Internal node: `H(0x01 ‖ left ‖ right)`.
- Empty leaf: Z_0 = `H(0x02)`. Empty subtrees then hash to Z_{i+1} = `H(0x01 ‖ Z_i ‖ Z_i)` without a special case. A new shard's root is Z_18.
- **Canonical rule:** a leaf whose 2m count bytes are all zero is Z_0, never `H(0x00 ‖ …)`. Counts only increase in `buy()`, so an updated leaf is never all-zero.
- Bit i of the rank (least significant first) is 1 when the running node is the right child at level i (the M0 convention).

### 3.3 Path data

- Siblings for one combination: a flat 576-byte string (18 × 32), bottom level first.
- `buy()` takes one flat string of 576 × b bytes and checks its length before slicing (H5).
- The leaf data for one combination is its 2m count bytes before this slot's increment. Slots that share main numbers see the counts left by the earlier slot (the builder supplies them in order).

## 4. State layouts

SilverScript encodes state as consecutive fixed-size fields, each behind a push prefix (`silverscript-lang/src/compiler/compile/state.rs:57-74`). An `int` is an 8-byte payload, a `byte` 1 byte and a `byte[N]` N bytes (`type_system.rs:47-58`). The tables give the field order, which is the byte order.

### 4.1 Shard (role 0x02)

| # | Field | Type | Range checked in `buy()` |
|---|---|---|---|
| 1 | role | byte | = 0x02 |
| 2 | round | int | ≥ 1 |
| 3 | shard_index | int | 0..K−1 (≥ 0; K is checked by `close()`) |
| 4 | m | int | 2 ≤ m ≤ M_HARD |
| 5 | price | int (sompi per combination) | 1 ≤ price ≤ PRICE_MAX |
| 6 | d | int (sompi per combination) | 1 ≤ d ≤ DEPOSIT_MAX |
| 7 | s_R | int (bp) | 0 ≤ s_R ≤ S_R_MAX |
| 8 | T | int (absolute DAA) | 0 ≤ T < 500,000,000,000 |
| 9 | root | byte[32] | — |
| 10 | S | int (gross sales, sompi) | 0 ≤ S ≤ SALES_MAX − P |
| 11 | P_R | int (referral paid, sompi) | 0 ≤ P_R ≤ S |

Value: S − P_R + R. `buy()` checks only the change in value, so R is not stored.

### 4.2 Ticket (role 0x05)

| # | Field | Type | Value at creation |
|---|---|---|---|
| 1 | role | byte | 0x05 |
| 2 | round | int | shard.round |
| 3 | T | int | shard.T |
| 4 | b | int | bundle size, 1..B_MAX |
| 5 | bundle | byte[6 × B_MAX] | the b canonical combinations in buy order, then zero bytes |
| 6 | claimed | byte[ceil(B_MAX / 8)] | all zero |
| 7 | payout_class | byte | 0 = P2PK Schnorr, 1 = P2PK ECDSA, 2 = P2SH |
| 8 | payout_key | byte[33] | class 0: 32-byte key + 0x00; class 1: 33-byte key; class 2: 32-byte script hash + 0x00 |

Value: d × b. The payout scriptPubKey is rebuilt as version 0x0000 ‖ script, where script is `0x20 key 0xac`, `0x21 key 0xab` or `0xaa 0x20 hash 0x87` (`standard.rs:19-37`; scriptPubKey bytes are version big-endian then script, `crypto/txscript/src/lib.rs:912-913`).

## 5. `buy()` transition

### 5.1 Shape

| | Index | Object | Covenant ID |
|---|---|---|---|
| Input | 0 | shard (round r) | cov |
| Input | 1..n, 1 ≤ n ≤ 8 | buyer funding | zero |
| Output | 0 | shard successor | cov, authorized by input 0 |
| Output | 1 | ticket | cov, authorized by input 0 |
| Output | 2 | referral, only if `with_ref` | zero |
| Output | last, optional | buyer change | zero |

So tx.outputs.length = 2 + with_ref + has_change, with has_change ∈ {0, 1}. That gives four enumerated shapes.

### 5.2 Arguments (sigscript)

`buy(int b, byte[] bundle, byte[] leaves, byte[] siblings, bool with_ref, byte payout_class, byte[33] payout_key, byte[] ticket_prefix, byte[] ticket_suffix)`

None of these is trusted. Each is checked against committed data (R8):
- `bundle`, `leaves` and `siblings` against the root and canonical rules;
- `with_ref` against the output shape;
- the payout fields against canonical classes;
- `ticket_prefix` and `ticket_suffix` against TICKET_TEMPLATE_HASH.

### 5.3 Checks, in order

**Shape and binding (R2, R6)**
1. this.activeInputIndex = 0; cov = OpInputCovenantId(0).
2. 2 ≤ tx.inputs.length ≤ 1 + F_MAX; every input i ≥ 1 has OpInputCovenantId(i) = zero (unrolled over F_MAX, guarded by i < length).
3. OpCovInputCount(cov) = 1.
4. OpAuthOutputCount(0) = 2, OpAuthOutputIdx(0, 0) = 0, OpAuthOutputIdx(0, 1) = 1, OpCovOutputCount(cov) = 2.
5. extra = tx.outputs.length − 2 − with_ref ∈ {0, 1}. Every output at index ≥ 2 has OpOutputCovenantId = zero.

**Time (R3, D4)**
6. OpTxInputDaaScore(0) < T.

**Ranges (R8)**
7. The state fields are in the ranges of 4.1; 1 ≤ b ≤ B_MAX.
8. bundle.length = 6b, leaves.length = 2m × b, siblings.length = 576 × b.

**Counter (per slot i < b, unrolled B_MAX times, guarded by i < b; running root starts at state.root)**
9. Combination i is canonical (3.1); rank from BINOM.
10. counts = leaves[2m·i .. 2m·(i+1)]; c = counts[2(bonus − 1) .. 2·bonus] as int; 0 ≤ c ≤ COUNT_MAX − 1.
11. old leaf = Z_0 if counts = ZERO_COUNTS[0 .. 2m], else H(0x00 ‖ rank ‖ counts).
12. new counts = counts with that slot replaced by (c + 1) as 2 bytes; new leaf = H(0x00 ‖ rank ‖ new counts).
13. Walk the 18 levels with siblings[576·i ..]. The old leaf must reach the running root, and the new leaf gives the next running root.

**Money (5.1, 5.5, R7)**
14. P = b × price; r = with_ref ? floor(P × s_R / 10⁴) : 0. With B_MAX ≤ 10 (asserted by a test), P ≤ 10 × PRICE_MAX = 10¹² and P × s_R ≤ 1.5 × 10¹⁵ < 2⁶³; d × b ≤ 10¹¹.
15. with_ref ⇒ r ≥ M_REF, tx.outputs[2].value = r, and the referral scriptPubKey is one of the three standard forms of D11.
16. tx.outputs[0].value = tx.inputs[0].value + P − r.
17. tx.outputs[1].value = d × b.

**Successor and ticket (R1, R5, R7)**
18. validateOutputState(0, shard state with root = final running root, S = S + P, P_R = P_R + r, every other field unchanged).
19. payout_class ∈ {0, 1, 2}; for classes 0 and 2, payout_key[32] = 0x00.
20. validateOutputStateWithTemplate(1, ticket state of 4.2 built from the fields above, ticket_prefix, ticket_suffix, TICKET_TEMPLATE_HASH). The bundle field is `bundle` followed by 6 × (B_MAX − b) zero bytes.

The change output is unconstrained apart from its index and zero ID. It belongs to the buyer.

### 5.4 Conservation (5.5)

Over economic value, excluding R:

> Σ funding = (P − r) + r × with_ref + d × b + change + fee

S grows by P and P_R by r. Derived per round (tests only; computed for real by `close()`/`draw()` in M2/M3), with share values used in tests s_F = 500, s_C = 50, s_D = 50, s_t = (200, 300, 500) bp, and s_H = 10⁴ − s_F − s_R − s_C − s_D − Σs_t:
- F, C_close, C_draw, each B_t and H = floor(S × s / 10⁴);
- b_r = S − P_R − F − C_close − C_draw − ΣB_t − H ≥ 0.

## 6. Ticket template (M1 placeholder)

`covenants/ticket.sil` declares the 4.2 state and one entry, `locked()`, that always rejects. It has no other code. Its prefix and suffix are what the shard's TICKET_TEMPLATE_HASH commits to.

## 7. Off-chain code (Rust)

- A new workspace crate `crates/lottery`:
  - `smt`: the sparse tree of section 3, with proofs, an empty-subtree cache and the canonical empty rule;
  - `combo`: canonical combination and rank;
  - `state`: shard and ticket encoders identical to SilverScript's layout;
  - `buy`: a builder for the four shapes (tests in `crates/lottery/tests/`, corrected from `crates/harness/tests/`: `lottery` depends on `harness`). It fills per-input compute budgets with `ComputeBudget::checked_covering_script_units` and signs funding inputs with real Schnorr P2PK keys (fixing the M0 OpTrue stand-in gap).
- Tests in `crates/harness/tests/m1_*.rs`, using `harness` for compile, engine run and masses with production flags.

## 8. Tests

Every test runs the full transaction through the v2.1.0 engine with production flags and the compute budget the builder commits. An attack test passes only if the shard input fails with a script verification error, not a budget error, unless the attack is the budget. Each attack changes one thing from a valid transaction, so the failing check is isolated. Where a check has two sides, both are tested.

## 10. Done criteria (from `docs/milestones.md`, made concrete)

1. P1–P5 pass: each bundle increments each combination's bonus count, and S and P_R grow by P and r.
2. The shard value grows by exactly b × price − r (P1, P2, P9; A18).
3. The ticket carries the bundle, a zero claimed bitmap, value d × b and a standard payout script, and is authorized by the shard under the instance covenant ID (P1, P2; A4, A19, A21, A22).
4. Repeated combinations and combinations sharing main numbers update correctly (P3, P4).
5. The referral pays exactly floor(b × price × s_R / 10⁴), only when ≥ M_REF; omitting it leaves the share in the shard (P9; A20).
6. Conservation holds in every positive test, and the derived F, H, ΣB_t and b_r satisfy b_r ≥ 0 (P13).
7. The ticket records T (P1; A7).
8. A1, A2, A6, A7, A8, A9 and A10 fail as specified.
9. Every test runs with production flags and committed budgets; A11 fails.
10. A12–A24 fail as specified.
11. `docs/costs.md` records M-a through M-d, the chosen B_MAX and the K it allows at `close()`; M-e is recorded in `docs/tn10-mass-check.md`.
12. `cargo test` passes in full (M0 tests included), the covenant-reviewer has run, and DECISIONS rows D1–D15 plus the B_MAX and hash results are written.
